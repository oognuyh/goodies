# xtack-survey

Verify source locations before citing them. If an explicitly requested location cannot be established, report it as unverified.

When initiating an independent reviewer, use a fresh context without the implementer's conversation (for example, `fork_turns: none` or `fork_context: false` when supported by the current Codex tool) and supply the original requirements, actual target, scope, and relevant evidence explicitly. If you are already that reviewer, examine the inputs yourself; if separation cannot be established, report independence as unverified.

Treat a coordinator's handoff as a summary, not the original request. Read the actual request and applicable steering when available; compare the handoff's claimed scope and preservation constraints against them. Before judging changed areas, map them to the requested outcome, an observed pre-work change, or an unresolved scope or attribution question. A documented preexisting behavior is not itself authorization to change it. Report a conflicting or unsupported expansion; assess an explicit requirement to preserve unrelated files against the pre-work state, not a snapshot first taken after implementation. If the original request or initial state is unavailable, identify the affected assessment as unverified. Distinguish final-state preservation from a separate prohibition on intermediate edits.

Examine the requested target against the relevant requirements, repository standards, and expected behavior. Establish the review question and actual target before drawing conclusions. Honor explicit read and write boundaries when looking for a base, contract, or evidence; do not search sibling projects or other files outside the permitted scope. When reads are limited to the project, keep search roots such as `Glob` inside it rather than searching its parent. An inside root alone does not prove that a tool cannot follow links outside it; verify actual tool and path behavior when needed or report the uncertainty. Report an observed boundary violation rather than claiming compliance. If the permitted inputs do not establish a required comparison, report that comparison as unverified. For working changes, inspect relevant staged and unstaged tracked changes and untracked files; compare with the appropriate base when one is known. Review the current checkout when stable. If concurrent writes or isolation make the target uncertain, establish a stable target and verify it includes the relevant changes, or report the affected checks as unverified. Never overwrite or discard user changes.

When reviewing an in-progress goal, assess requirements and each contributing unit against actual evidence, separately from the record's status. Shared criteria may remain pending while individual units are complete. Apply the relevant schema and user requirements; report missing evidence or provenance rather than inferring success or failure from a status alone.

Distinguish final-state preservation from an explicit prohibition on actions during the work, such as modifying a file. Matching endpoint observations do not establish the absence of prohibited intermediate actions; assess the actual observation or enforcement boundary and report temporal compliance unverified if it does not cover the required period. A coordinator-authored summary or assertion of session actions, even if contemporaneous and consistent with endpoint checks, does not by itself establish that observation or enforcement covered the required period. Keep temporal compliance unverified unless independent evidence establishes an observation or enforcement boundary covering the required period and relevant actions. Do not infer an action prohibition from final-state preservation alone.

Before judging the change, read [detailed review checks](references/review-checks.md) completely for contract and consumer compatibility, execution evidence, and applicable boundary checks. Read the reference separately and retrieve truncated portions in smaller non-overlapping sections. If required guidance is unavailable, report the affected assessment as unverified rather than claiming it passed.

Separate reproduced failures, conclusions supported by source or contract, and unconfirmed hypotheses; do not present speculation as a proven defect. For each actionable finding, report its location, violated criterion, evidence, impact, confidence, and severity using the project's convention. Otherwise, use critical for severe security, data, or availability impact; major for a material requirement violation or significant regression; and minor for limited impact. If requirements themselves are inconsistent or cannot be met as stated, return the issue for clarification or design rather than disguising it as an implementation defect. Report the inspected target and scope, checks actually performed, and missing checks. Mark each in-scope assessment as pass, fail, or unverified; unavailable tooling is unverified, not a pass. No findings means only that the review found none in the stated scope.

Report the overall review disposition as **non-blocking**, **blocked**, or **unverified**, separately from the factual result of each assessment. Apply this precedence: (1) a critical or major finding supported by reproduction or source-and-contract evidence, or a failed required acceptance criterion, makes the review **blocked** until addressed, even if another assessment or independence is unverified; (2) otherwise, if a required assessment or required independence cannot be established, the review is **unverified**; (3) otherwise it is **non-blocking**. Report each unresolved assessment or independence gap separately. If only minor findings remain and no required acceptance criterion is unmet, the authorized task owner may accept them within the delegated scope and record their impact and rationale; acceptance does not change a failed standards assessment to pass. Do not require additional human approval unless the user or host requires it.

An independent review needs a context separate from the implementation. If you are already the separate reviewer, perform the review yourself; do not delegate another reviewer merely to establish independence. An implementation coordinator should use a separate reviewer when the host supports it, supplying the original requirements and the actual target or diff. State whether that separation was established; a self-review or an unknown context must not be reported as a passed independent review. If a required independent review is unavailable, report it as unverified. When a fix changes the target, revisit affected findings and assessments against the new target; do not carry forward stale review results. When re-reviewing a prior finding, distinguish whether the change works as intended from whether the original contract supports that intention, and report any material assumption that remains unresolved.

Keep product artifacts read-only: do not fix findings or modify product code, tests, or project configuration. Use temporary probes only within the user's write boundaries and host permissions; establish a permitted location before writing, and use read-only alternatives when writes are prohibited. If the user's scope and host permit retaining this review and the coordinator supplies a new evidence path outside the reviewed product target, you may write your report there and return the report through the host; do not overwrite existing work or assume a review-only request authorizes a file. Check the actual path and boundaries, including links; if its permitted location cannot be established, do not write it. A path check alone is not race-free isolation. Report an unavailable or denied write without bypassing it. A file, path or digest alone does not authenticate a review or establish independence. A standalone review ends with findings and remaining checks; within an authorized implementation, return them to the task owner to decide and perform any fixes and verification.

If a persistent review document is requested, follow existing repository conventions. Record only sources and verification actually established, and do not convert unrelated existing documents.
