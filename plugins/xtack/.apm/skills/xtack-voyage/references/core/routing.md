# Routing a Voyage goal

Selecting Voyage to coordinate the user's outcome begins its own goal. A separate reviewer consulting these instructions to assess an existing goal does not start or continue it; inspect the permitted record and return the review to its owner. The user's actual request, explicit later steering, and applicable host instructions, constraints, and permissions define the outcome and stopping point. When coordinating, preserve the request and steering in the identified Voyage record when permitted storage is available; otherwise use session state and disclose the recovery limitation. Investigate the repository, product behavior, existing decisions, and available tools before filling in facts. State consequential assumptions as assumptions. Derive observable acceptance criteria and scope, including exclusions; do not quietly replace a broad objective with an easier one. Link each unit and proposed specialist action to the user's outcome, a required criterion, or a necessary dependency. A newly discovered improvement is not itself authorization to broaden the work. In unattended work, resolve delegated choices and keep progressing without a routine interview. If essential intent or authority truly cannot be established, finish independent work and report what remains blocked.

Classify each independently verifiable unit, rather than forcing a large outcome into one type:

| Work | Playbook | Starting signal |
| --- | --- | --- |
| Restore behavior | [bugfix](../playbooks/bugfix.md) | A failure, regression, or incorrect result is reported. |
| Add or change behavior | [feature](../playbooks/feature.md) | A new outcome or change to a product contract is authorized. |
| Restructure behavior | [refactor](../playbooks/refactor.md) | The primary objective is a safer or clearer implementation with preserved behavior. |
| Establish facts | [investigate](../playbooks/investigate.md) | Diagnosis, research, or verification is the requested stopping point. |

An objective can contain multiple types. Reclassify when investigation changes the actual problem; track dependencies and verify integration back against the original objective. For a substantial outcome, plan separately verifiable units with results, scope, acceptance checks and dependencies. Record the actual state if work has already begun; use session state if a durable record or suitable planning tool is unavailable. Verify each unit before marking it complete and honor actual dependency and user-required ordering. Keep inseparable changes together, and do not split a small coherent change merely to create units. Delegate independent work when parallel progress or a necessary perspective is likely to outweigh coordination, and protect shared writes. This does not waive explicitly requested delegation, required independent review, or ADR stakeholder analysis. Give workers the relevant scope, target, requirements, constraints, and completion conditions.

Select the smallest relevant set of specialists when available: `xtack-chart` for user-led intent clarification, `xtack-keel` for consequential technical design, `xtack-trace` for diagnosis, `xtack-forge` for implementation, `xtack-survey` for review, `xtack-trial` for verification, and `xtack-wake` for observed recurring or consequential failures. A direct specialist invocation is also valid. Do not run all specialists for every unit; unattended work does not introduce an interactive chart interview. When a specialist or host capability is unavailable, use an available method and explicitly report any resulting gap.

The execution core's `playbook` array lists candidate specialists, not a required sequence or a command to invoke each skill. Apply its `requirements` and the actual task risk separately: for example, a Light change needs relevant execution checks, but its route does not require a separate reviewer. Standard and Critical changes still require independent review and the relevant execution checks, whether or not a named specialist is separately loaded. Honor a user's explicit review request at any risk level.

Consult the relevant host guide when host-specific behavior matters, including when recovery across sessions is required: [Codex](../adapters/codex.md) or [Claude Code](../adapters/claude-code.md). Consult the budget policy when limits or retries need assessment and the state guidance when its dispositions or gate rules are needed. For another host, use only capabilities actually available in that session. Do not read every playbook or reference by default.
