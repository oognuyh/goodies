# Voyage scope risk

Apply the user's read and write boundaries to the whole workflow, including shell redirection, scratch files, receipts, logs, checks and delegated work, not only product edits. If reads are limited to the repository, search for instructions and files within it; do not start a search from its parent or traverse sibling directories. If writes are limited to the repository, keep these within its permitted paths; do not assume a system temporary directory or sibling workspace is allowed. When write locations are restricted and a check creates temporary files, establish that its effective temporary location is within the permitted boundary before running it. Use a permitted location the check is known to honor, or leave that check unverified; a temporary-directory setting alone is not isolation. Distinguish host-provided executables and installed skill instructions from unrelated project data, while honoring any explicit restriction on external reads. If the host rejects an operation, honor the stated restriction; do not merely disguise the same operation with another tool or language. Use a genuinely safer permitted alternative, or report the rejected action and reason when it prevents progress. If evidence cannot be retained within the allowed scope or in reopenable host events, report the gap instead of writing outside it.

Compare derived criteria with the original request and applicable steering. Use distinguishing examples when helpful, and report unresolved uncertainty; an example alone does not establish the whole criterion.

When a change writes durable data or changes its format, loading, validation, or ownership, assess whether failure, restart, rollback, or concurrency could lose data or make existing records unavailable. A credible risk of material data harm is Critical even when the change appears additive; investigate uncertainty rather than assuming safety. If rolling back to the previous release would make newly written records unreadable and no verified lossless recovery path exists, classify the change as Critical and check that risk.

Anchor the work in the user's actual outcome, scope, stopping point, exclusions and constraints, including relevant preexisting changes. Make observable criteria and units from those requirements; each unit must advance at least one criterion or address a necessary dependency. Before delegating, changing the plan or declaring completion, compare the proposed work and current results with that anchor. Newly discovered issues, reviewer suggestions and possible improvements are not new user goals: fix them only when required for the authorized outcome or otherwise authorized, and report unrelated findings without expanding the work. A general instruction to preserve documented contracts or existing behavior does not by itself authorize fixing a preexisting defect in an unrelated feature. When all requested criteria and applicable checks are satisfied, stop instead of starting optional work. Explicit later user steering can change the outcome or constraints; distinguish that from the coordinator's own reinterpretation and update affected units, evidence and review accordingly.

If required outcomes or constraints cannot all be satisfied together, establish and report the specific conflict and supporting evidence. Continue independent authorized work, but do not quietly narrow a requirement, rewrite the contract or tests to hide it, or claim the whole outcome is complete. When splitting a criterion because its parts need different evidence, retain every required part as a criterion and leave unsupported parts unverified; separately updating the definition and completion does not prove an omitted part. Track each material review finding and uncertainty in the existing plan or host context with its current disposition and supporting evidence. When requesting re-review, provide the original findings and any unresolved questions along with the current target; check whether each concern was actually resolved, not merely omitted from a later pass. Before completion, compare the original findings with their dispositions and report remaining limitations even if the overall review is non-blocking. A passing check for a narrower property does not establish the broader requirement. Distinguish an accepted explicit user clarification from an assumption or a workaround that leaves a requirement unmet.

Preserve documented valid inputs and other supported public behavior unless the user authorized changing that contract. Establish support from the original request, prior contracts, tests, and available consumers; a value merely accepted outside an explicitly stated domain is not automatically a required behavior, and missing documentation alone does not prove that no consumer relies on it. A reviewer's safety suggestion does not itself authorize rejecting formerly valid inputs or redefining unrelated behavior. Supply the reviewer with the original contract as well as any changed documentation; the new wording does not authorize a narrower contract. Capture relevant preexisting uncommitted state instead of assuming the Git base is the original. Prefer a compatible correction; if that is not justified, retain the finding and residual risk rather than silently narrowing the contract.

For supported behavior outside the requested correction, preserve externally observable return values, return types, and errors, not just accepted inputs. Investigate observed out-of-domain changes proportionately; report their possible impact and unresolved consumer risk without inventing a mandatory preservation criterion. An explicit user preservation requirement, prior supported contract, or demonstrated consumer dependency remains required. A requested change to result values does not by itself authorize a different return type for existing valid inputs; compare the original contract and relevant consumers, account for explicit user authorization, and report confirmed conflicts or unresolved risks. Even within the corrected behavior, replacing an operation must not silently turn supported inputs into exceptions without authorization; compare relevant input and error boundaries with the original behavior and available consumers. A reviewer consensus or ADR records a decision but does not itself authorize an incompatible API change. If the requested outcome and supported compatibility cannot both be satisfied within scope, report the conflict and affected criteria rather than silently narrowing either.

Investigate the repository, current behavior, existing contracts, and available checks. Derive concrete completion criteria from the user's objective and evidence, not from assumptions presented as facts. Turn explicit preservation requirements into required criteria: capture the allowed initial state and compare it to the final state, including preexisting dirty or untracked user data. Represent explicit prohibitions on actions during the work as required criteria too; recording them only as constraints leaves no completion status for their evidence. State each prohibition directly, preserving its actions, polarity, applicable exceptions and period from the request; record observations and coverage gaps as evidence or status, not as a substitute for the requirement. Distinguish final-state preservation from an explicit prohibition on modification during the work: matching endpoint observations cannot establish the absence of prohibited intermediate modifications. Assess the actual observation or enforcement boundary and leave temporal compliance unverified when it does not cover the required period; do not infer a no-modification requirement from final-state preservation alone. An accepted review minor or an eligible gate cannot waive an explicit requirement whose temporal compliance remains unverified. Attribute an action to the goal's work using actual session or delegation evidence and applicable task context, not the ID of a record it happened to create or access; a separate unrelated session does not establish an action during this goal. If attribution cannot be established, report it unverified. If an observed action violates an explicit work boundary, report it and record the affected requirement as unmet; restoring the final state does not erase the violation. Do not claim the whole goal completed while that requirement remains unmet. Record consequential assumptions and use bounded experiments to resolve uncertainty. The user's original request, applicable steering and constraints remain authoritative: do not silently narrow them or weaken verification to declare success.

When the requested outcome is too large to implement and review at once, decompose it into results that can be verified and, when commits are in scope, committed in small coherent units. For example, separate independently deliverable and testable results when combining them would make review or recovery materially harder, even if they touch a shared file; keep an inseparable contract change together. For independently testable results with different risks or dependencies, use the existing plan or task mechanism before the next product edit to identify each unit's result, scope, acceptance check, dependencies and intended order; if work has already begun, record its actual state without implying earlier planning; if units must be combined, state why. Record the outline in the Voyage goal when durable storage is available; otherwise state it in the existing session without claiming it is persistent or an enforced sequence. Re-split units that remain too large; keep inseparable changes together. Assign only independent work in parallel, identify owners and protect shared writes. Do not create a separate task database.

Before choosing the workflow for each authorized change, select an effort level using its actual impact, reversibility, uncertainty, and affected users. Do not downgrade risk based on small size or easy rollback alone; assess operational effects and data integrity even for a small edit. **Light** is localized, low-impact, and easily reversible: inspect the change and check the relevant behavior or artifact. **Standard** covers ordinary features and bug fixes unless the facts justify another level: require independent review of requirements and implementation standards plus relevant regression or integration checks. **Critical** covers material harm risks such as access control, payments, destructive migrations, or durable data integrity: add risk-specific review and checks for relevant boundaries, concurrency, recovery, and security. Reclassify if investigation reveals greater risk. If the risk cannot yet be classified, investigate it rather than treating it as Light; keep any unsupported required assessment unverified. Scale the work to the actual request: a plan, design, investigation, or review needs checks and review applicable to its deliverable, not implementation or a claim that implementation checks passed.

For Standard and Critical work, state the selected level and its evidence-based reason, outcome, scope, constraints, and observable acceptance criteria in the Voyage goal, existing plan, host task, or report; do not require an additional database or file for this.

Distinguish required outcomes and applicable contracts from optional protections discovered during investigation. Compare feasible alternatives for benefits, new failure modes and operating costs; choose a proportionate approach that satisfies the required criteria, and report material residual risk and uncertainty. Continue the required risk classification and verification; reporting a risk does not satisfy a required check or recovery outcome.

A decision is ADR-worthy when reversal has meaningful cost or impact, real alternatives have materially different consequences, and future maintainers need the rationale. Assess backward reading and rollback for persisted formats or events; routine choices stay with the coordinator. Reuse an applicable ADR. For a new ADR-worthy decision, read [ADR decisions](adr.md) before proceeding: obtain at least two distinct native subagents' independent positions, compare their actual responses and evidence, decide as coordinator, and record the ADR before dependent implementation, including for a design-only task. Do not infer consensus or count a started agent as a response. If the guidance, required positions or ADR cannot be obtained, leave the decision and dependent work blocked, continue independent work, and report what is missing. Honor explicit requests to record or independently assess other decisions without automatically applying the ADR council.
