# Voyage goal lifecycle

Selecting Voyage to coordinate the outcome starts a Voyage goal. Before the next product edit, check whether storage is permitted and available; if Voyage was selected after earlier edits, record their actual state without implying earlier planning; follow the [goal store guide](../scripts/GOAL.md) to create a new record or resume the explicitly identified one, and inspect the actual result. If unavailable or prohibited, use the session-only fallback and report why and the persistence gap. Consulting Voyage only to review an existing goal does not start or continue it. Plan verifiable units and their actual dependencies, verify units before marking them complete, and honor any required ordering. Independent units may proceed in parallel with separate ownership and checks. A goal record does not enforce order; report the sequence observed and any ordering requirement that remains unverified.

Honor an explicit user request to start or resume a goal. When reviewing an existing goal as a separate reviewer, inspect the permitted record and evidence, and return the review to its owner. If you are already the separate reviewer, do not delegate another reviewer merely to establish independence. Establish the original request, scope, exclusions, stopping point, explicit constraints, observable criteria, and appropriate units when coordinating a goal. After establishing the goal and again before completion, compare the actual request and applicable steering against the recorded criteria, units and constraints, including their scope and periods; correct mismatches and reassess affected work before further dependent edits. When stopping after goal definition, make this comparison before reporting and describe the actual recorded criteria accurately. Make the same comparison for a session-only goal. When the user explicitly requires recoverable progress or evidence, include that requirement in the criteria and assess whether a later session can access what was requested; a goal status alone does not establish this. Preserve exclusive qualifiers such as "only" and "do not" where they define a boundary. Record later explicit steering separately and update affected work without rewriting the original request. Drive the goal toward evidence-backed completion using the host's actual capabilities.

For a request that stops at a plan, design, investigation, review, or verification, make the requested deliverable and its applicable checks the current goal. Future implementation steps, dependencies, and acceptance checks belong in that deliverable, not as pending implementation units or unmet product criteria for the current goal. Preserve the actual plan in a permitted artifact or an existing record's text/reference so it can be recovered; report a persistence gap if it cannot be retained. Link the deliverable criterion to a unit that produces or verifies it, complete that unit when supported by actual evidence, and stop when the requested deliverable is complete. This does not authorize or claim implementation. On resuming such a goal, check whether its existing criteria incorrectly require the inspected subject to pass instead of requiring the requested assessment and report. If authorized, correct that mismatch while preserving every requested condition, actual findings and prior history; reassess the revised criteria against their evidence. A completed assessment can report a failed subject. If the user actually requests an ongoing implementation goal with a planning checkpoint, retain the implementation criteria and units instead.

Create the versioned goal in a new caller-selected directory within the user's writable boundary. If Voyage is selected after product edits, record the actual state without implying earlier planning. Treat a review-only request as read-only unless the user authorizes a record; when a record is prohibited, keep the goal in the session. When a record exists, explain its location, minimize retained sensitive information, and do not change ignore rules automatically. Each revision retains its own contents, including original constraints; change current constraints only in response to actual user steering and preserve the original request. Keep the identified goal current as steering, units, evidence, or status changes.

When recovery would benefit and the user and host permit the path details in tool output and its retention, request the store's optional locator with the goal result. Treat it as a lookup hint, not authentication or proof that the response can be reopened; retain independently observed identity anchors when available. Older stores may reject the option, so inspect the actual error and use a permitted known path or original input event when available.

If the user explicitly excludes material from the durable goal and the workflow cannot establish that a goal write will respect that exclusion, do not create or update a free-text goal record through that workflow. Instructions or the agent's intention to omit content do not establish an effective boundary; assess any independent controls against the actual restriction and all goal fields. Continue authorized work in session state and check whether another permitted, accessible artifact or host event meets the recovery requirement. Report any recovery gap; leave a required recovery criterion unverified if recovery cannot be established. If a goal already exists, stop affected further writes; do not silently erase or rewrite its history. The store cannot enforce content exclusions, and session state does not prevent retention by host transcripts or other tools. If those are also restricted, assess actual host controls and report any gap.

Use the returned goal ID and revision; do not overwrite a different goal or silently discard a conflict, unknown version, incomplete history, temporary artifact, or empty goal directory. Record progress and findings in statuses and evidence rather than rewriting unit outcomes or criterion descriptions as reports: the store treats definition changes as requiring reassessment. Refine definitions when needed or change them when the work or requirements change. Resume only an explicitly identified goal, never whichever happens to be newest. On recovery, provide a previously observed revision as `minimum_revision` and independently observed goal ID as `goal_id` to `show` when available. The store rejects an ID mismatch; do not treat or update a different record as that goal. If `show` reports completion warnings, inspect and reassess the affected claims; the absence of warnings does not verify evidence. If the ID is unavailable, report that identity continuity is unverified. An ID match does not authenticate the record. Without an independent anchor, the latest revision can be removed or modified without guaranteed detection; revision hashes do not authenticate history. If permitted storage or the store is unavailable, manage the goal in the current session, continue authorized work, and report that recovery is not assured. A record is not a scheduler and cannot start another turn.

When work stops before the requested outcome is complete, report the last observed goal status, remaining work and material gaps; mark the status unverified if it is unavailable. If a goal record exists and disclosure is permitted, also give its directory, the goal ID and latest revision actually observed from the store, so a later session can identify it; distinguish any unknown value rather than guessing. If no usable record exists, say that recovery is not assured. These details help a later session find and assess the goal; they do not start one, authenticate the record or replace current evidence.

Before completing the goal, reconcile each criterion's recorded status and final report with current evidence and review limitations, and each unit with the original outcome and applicable steering. When a later notification or continuation ends the work, report the overall outcome, material choices, actual evidence and remaining gaps in a final response understandable on its own, not only the latest finding. Leave a required criterion unverified in the record and report when it is not established; a separate applicable observation can establish it even if one reviewer could not. When a retained gate assessed the goal or relevant criteria, distinguish its scope and assessment at that time from the current goal judgment: identify later evidence that resolves a specific earlier uncertainty and do not describe the old gate as evaluating it. When a current gate is required or used for the judgment, reevaluate changed inputs and conditions using the execution guidance; retain the earlier assessment when permitted. Implementation using the core requires a current gate even when other evidence is available. A verification or investigation goal can report directly assessed evidence without adding a gate solely because an older gate exists; honor any independently applicable gate requirement. Once planning is complete, link each goal criterion to at least one unit; a prerequisite unit may instead lead to a linked unit through dependencies. An unfinished record may temporarily have unlinked criteria, but resolve those links before completion. When recovery matters, reference evidence that a later session can actually access when permitted; if only ephemeral session output is available, state that limitation rather than implying the original observation can be recovered. If a deliverable must be recoverable, compare the retained version with what will be delivered, including material conditions and ownership; reconcile differences before completion or report what remains unverified. A later read of the current target is a new observation, not the earlier output. If recoverable evidence is a required criterion and cannot be established, leave that criterion unverified. Update the record with the actual results, then use `completed` only when its structural completion checks pass and the coordinator has verified the real evidence. `blocked` records a genuine blocker; use `active` when continuing a previously blocked or completed record after reassessment. A status update records a conclusion, not permission to publish or proof the host will execute another turn.

Honor applicable host instructions, constraints, and permissions. The Voyage record does not replace the original request or later steering.
