# Codex host boundary and resumption

Voyage starts and manages its own goal for the user's outcome, using its bundled file-backed record when storage is permitted and available. Honor applicable host instructions, constraints, and permissions. Instructions and a local gate cannot intercept every host tool call, guarantee sandbox isolation, change the user's authority, or ensure that a later turn automatically occurs.

The [skills guide](https://developers.openai.com/plugins/build/skills) describes scripts and references bundled with skills and loaded when relevant. Check the actual host and installation route for the capabilities available in this run. Codex documents [permission profiles](https://developers.openai.com/codex/permissions/#file-access-limited-to-workspace) for sandboxed local commands, including a workspace-limited example. The documented example permits `:minimal` runtime paths; other required skills and tools may need additional access. Profiles do not by themselves govern MCP, connectors or browsers. Assess the effective host controls and report an unenforced or unverified requested boundary; do not infer isolation from a worktree or the agent’s instructions.

Use native subagents when available and appropriate. For independent review or an ADR stakeholder position, start a fresh context without the implementer's conversation (for example, `fork_turns: none` or `fork_context: false` when supported by the current Codex tool), and explicitly supply the relevant goal, requirements, target, evidence, scope, and read/write constraints. For a new ADR-worthy decision, two distinct subagent contexts must supply positions before the coordinator records the decision and begins dependent implementation; reuse an applicable ADR when one exists. A review is independent only when a separate reviewer context is established for the actual target and requirements; a model-authored label or different model alone is insufficient. Do not inspect a sibling workspace or other files outside the permitted scope to reconstruct an unavailable target; report uncertainty instead.

Use actual tool outputs for commands, Git, and CI. A successful command reports execution success, not automatically an acceptance pass. When required CI is available, associate the actual run and required checks with the relevant commit; a different commit or a clean CI run does not establish a pass for uncommitted changes. Account for relevant staged, unstaged, untracked, ignored, and external inputs where known. If the target or execution provenance cannot be established, report the affected evidence as unverified. Do not expose secrets or persist full environment variables and command output by default.

On a continuing turn or after interruption, recover only the explicitly identified Voyage record when available, the original request and applicable later steering and constraints, installed instructions, current target, previously observed evidence, outstanding units, and next action. If the record cannot be read or storage was unavailable, use the available host session and permitted evidence and disclose the recovery gap. Reuse only evidence still valid for the current target and conditions; rerun affected checks and review after changes. Do not claim Voyage goal completion because a budget expired, a run ended, or a local record or gate lacks required supporting evidence. Mark the Voyage record complete only after checking actual evidence. Report actual actions separately from readiness to ship.

When a retained reviewer thread ID is available and access to its actual Codex thread store is permitted, an available [Codex app server](https://learn.chatgpt.com/docs/app-server) may retrieve its stored history without resuming the thread: use `thread/read` for metadata and `thread/turns/list` or `thread/items/list` for the relevant items. For turns, request `itemsView: full` when supported. When supported, a known turn ID and small item pages can narrow returned data; the newest item alone is not necessarily the needed or final review, and partial pages do not establish complete history. A history request or direct file read can access other thread content even if only one response is needed; check that the actual read and output are permitted, and select needed fields before printing rather than dumping raw history. Preserve the complete reviewer response when its original wording is needed. Check pagination and match the actual reviewer response, target and time; do not treat an ID or a summary as the original output or proof of independence. Verify the actual host/store and permissions: a fresh or different store may return `not_found`. Starting an app server can write to its state directory, so do not start one where that write is prohibited. If the original cannot be reopened within the permitted boundary, report the recovery gap rather than searching unrelated stores or inventing a result. Retrieved host records are not self-authenticating.
