# Voyage execution

Start with [routing](core/routing.md) and load the selected playbook. Load its linked policy, state, and host references when their details are needed for the actual work; do not read a reference solely because it is listed. Consult the relevant host guide when host-specific behavior matters, including when recovery across sessions is required; consult the budget policy when limits or retries need assessment and the state guidance when its dispositions or gate rules are needed. These resources also support a bounded xtack task. Honor explicit read and write boundaries in all delegated work; if an input needed for review lies outside the permitted scope, report the affected comparison as unverified.

For Standard implementation, use the [execution core quickstart](../scripts/QUICKSTART.md) when mechanical target identity, evidence reuse or stale-state tracking materially helps: for example, independently progressing units, resume across changing inputs, multiple targets or checks needing reuse, user-required machine records, or required CI or approval evidence. For a bounded change whose current host checks and independent review can be directly inspected and linked to the criteria, assess those actual results without assembling a ledger by default. For Critical implementation, use the core when the runtime, authorized inputs and permitted record handling are available; if any is unavailable, state the actual limitation and use available evidence without claiming a core gate ran. For Light work, use it only when it materially helps. Decide before the first relevant post-change check; when using the core and the check can run through it, capture the initial execution with `run` instead of running the same check directly and again for a receipt. State a concise reason for the choice in the existing plan or report; do not downgrade risk or omit required verification to avoid a gate or review. Respect stricter user and host requirements.

If using the core, read and follow its [quickstart](../scripts/QUICKSTART.md) for routing, receipts, the gate, and proportional retention; for new Standard/Critical review-bearing gates use `gate` with the actual reviewer disposition; load the full reference or schemas only when needed. Check the gate's assessment and every reason against the actual outcome and current target. Reuse evidence only while its target and relevant conditions remain valid. The core evaluates supplied records; it cannot authenticate external claims, prove a test's assertions, or enforce host actions. Inspect actual host evidence and resolve missing, failed, stale, or unverified conditions rather than asserting a pass. If the core is unavailable, use available evidence, report the gap, and do not claim a gate ran.

When an evolving goal or evidence directory cannot share the product's exact gate target, assess the product and retention requirements separately as described in the quickstart, then reconcile the original goal and required reviews. In the final report, identify which criteria or scope the gate actually assessed and report the separate requirements and their evidence or gaps; do not present a product-scoped gate as a full-goal gate or disguise a unit's affected paths. If one machine-evaluated gate for the entire request is required but unavailable, report that gap.

Own the requested outcome in the receiving session. Select investigation, design, implementation, and review methods as needed, and review delegated artifacts against their actual inputs. Verify each unit before treating it as complete. For consequential guarantees, check plausible ways their assumptions can fail as state changes, not just the examples in the plan or ADR. Do not call a successful commit a successful verification or include unrelated user changes in a commit. After all units, verify their integration and the original request's completion criteria, including applicable user steering. When the user or dependencies require an integration check after specific units, use evidence from after those units completed and before recording integration unit or goal completion; an earlier check cannot establish that sequence, and a later check does not erase an earlier ordering deviation.

Connect each material completion criterion to evidence that directly observes or asserts that criterion and to its actual status; identify the target and relevant conditions in the existing plan, host task, or report. Use a test receipt only for the assertions the test actually makes. For an independently observed structural property or file preservation, connect the actual source or host output and target identity separately; an unrelated `node --test` receipt is not proof. If output was not captured, do not say the receipt shows detailed output: cite the observed original output or leave the unsupported claim unverified. Keep review findings and execution verification distinct: an available review does not prove execution passed, and passing tests do not resolve a blocking review finding. When the target changes, recheck affected evidence and review findings; do not reuse stale results as proof. A failed or unverified required acceptance criterion prevents completion; a required review or check must have actual evidence. If the requested outcome is to investigate or diagnose a failure, actually establishing that failure can satisfy the investigative criterion without implying the subject passed.

When a review's narrative leaves a required criterion unverified despite a pass label or accepted minor, assess the original review and actual criterion evidence separately. Preserve the reviewer's original verdict. If the criterion remains unverified, record that status in the permitted goal record or session and, when using the core, supply the unresolved observation as an unverified assertion bound to the current criterion before the gate, even if another entry asserts pass. Bind it to the target actually observed; if that target cannot be established, do not rebind an old review to the current target and report the gap. A separate applicable observation can resolve the uncertainty; explain the reassessment in the current gate input and retain the earlier ledger and review when permitted rather than silently erasing the concern or rewriting the review.

Regression checks should enforce the requested contract without narrowing it to an incidental implementation choice. Where multiple representations are explicitly or semantically equivalent, assert the required public properties; require exact bytes or formatting only when the actual contract requires them. Inspect the actual output at the boundary when a downstream parser or normalizer could conceal an invalid result; a transformed observation alone may not establish the original output's required properties.

When a documented numeric range reaches the runtime's precision or formatting limits, check relevant boundaries against an independent exact reference when practical, or state what remains unverified. Do not claim the entire range passed solely from ordinary examples or an expected value computed with the same potentially lossy operation.

Select only the specialists useful to the work, as described in routing. In unattended work, do not introduce an interactive interview; investigate and resolve delegated choices instead. If a specialist is unavailable, use available host methods and report any resulting verification gap.

Reuse an observed passing check while its target and relevant conditions remain valid; rerun it when changes, failures, a specific unresolved uncertainty, or an explicit user or host requirement justifies doing so. This does not replace a required independent review.

For a coordinator handling Standard and Critical changes, review and execution verification are separate required completion conditions. Give an independent reviewer in a separate context the original requirements and actual target or diff when the host supports it; use additional risk perspectives when warranted. Tell the reviewer who implemented the change and how the reviewer context is separate when established; identify unknowns instead of inventing them. Supply the relevant observed execution results for the current target. When permitted and practical, provide the relevant original output or a reopenable reference and identify the target; label summaries as summaries. Do not create storage or repeat execution solely for the handoff. The reviewer independently assesses the change and may run additional checks to investigate a specific failure hypothesis or uncertainty; do not repeat an unchanged check merely to duplicate an observed result. Light changes may use focused self-review. Reading a review skill, self-review, or changing models alone does not establish independence. Address blocking review findings and failed checks within the authorized scope, then repeat the affected review and verification against the changed target. If the necessary independent review or check is unavailable, record it as unverified, continue independent work, and do not declare the change complete. An independent review may conclude with an accepted nonblocking minor: keep its original axis verdict, including fail, and report its disposition, rationale, and residual risk. Never waive an unmet required acceptance criterion or a major or critical finding as minor. For these changes, a verified result means the required independent review finished with no unresolved blocking findings and the required acceptance criteria and execution checks passed for the current target; it does not authorize merging, publishing, or deployment beyond the user's scope and host permissions. If attempts repeat without new evidence or progress, change approach or gather missing evidence; when further progress is blocked, continue independent work and report the specific blocker. Do not impose a fixed number of retries or request user input merely because an automatic attempt failed.

For unattended work, investigate facts, choose delegated decisions, and record meaningful assumptions without interrupting the user. If essential intent cannot be established or permissions, tools, or resources prevent progress, complete independent work and report the exact blocker and evidence. Never fabricate a pass or bypass host permissions. A budget limit is not completion.

Follow existing project conventions for plans and other documentation; apart from the permitted Voyage goal record, create durable records only when they serve the work or are requested.
