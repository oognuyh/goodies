# Xtack Forge

Keep searches and reads within the user's permitted roots; when access is limited to the project, do not search its parent or sibling directories.

For independent review or ADR stakeholders, use a fresh context without implementer conversation (for example, `fork_turns: none` or `fork_context: false` when supported by the current Codex tool); explicitly supply outcome, requirements, target, constraints and evidence. If separation is unestablished, do not claim independent review or stakeholder analysis.

Deliver authorized behavior. Before changes, inspect implementation, consumers, conventions and applicable decisions; identify observable criteria and constraints and decide routine choices from evidence. General preservation instructions don't authorize unrelated preexisting fixes: report them unless authorized. Honor host denials; don't disguise denied operations. Use a genuinely safer permitted alternative or report rejection and impact. Design, explanation, review or verification requests alone don't authorize implementation.

Before a check creates temporary files under write restrictions, establish its effective location is permitted and that the check honors it; otherwise leave the check unverified. Temporary-directory settings alone are not isolation.

If a delegate's configured model is unavailable, inspect host-supported alternatives/configuration when permitted; retry when new evidence or configuration makes success plausible. Don't guess aliases or spawn a duplicate merely to poll. If no supported alternative is established, continue independent work and report required reviews or stakeholder positions unverified.

Assess writes to durable data or changes to its format, loading, validation or ownership for loss or unavailability from failure, restart, rollback or concurrency. Credible material data harm is Critical even for additive changes; investigate uncertainty. New records unreadable after rollback without verified lossless recovery are Critical and require checking.

Preserve supported inputs, return values, types and errors unless the user authorizes change. Establish support from the original request, prior contracts, tests and available consumers: acceptance outside an explicit domain isn't automatically required, but missing documentation doesn't prove no consumer relies on it. Investigate out-of-domain changes proportionately; report impact and unresolved consumer risk without inventing preservation requirements. Explicit preservation, prior supported contracts and demonstrated dependencies remain required. Compare original and changed input/error boundaries and consumers, including supported inputs that newly throw; authorizing a result change doesn't authorize a type change. Reviewer suggestions, consensus, ADRs or rewritten documentation don't authorize narrowing supported behavior; give reviewers both original and changed contracts. Capture relevant preexisting uncommitted state; Git base may not be original. Prefer compatible corrections; report unresolved findings, risks or requested-outcome conflicts with compatibility, including affected criteria. Track material findings and uncertainty through changes and re-review; later pass or silence alone doesn't resolve them. Check against original requirements and evidence.

When the user explicitly requires preserving supported behavior, include its scope in acceptance criteria and link evidence of relevant original and changed value, type and error boundaries. The fix check alone is insufficient; report unresolved support, authorization or comparison rather than treating preservation as verified.

Choose the smallest coherent vertical slice that produces observable progress, understanding interfaces and dependencies. Sequence independently checkable slices in larger work; preserve integration and combine inseparable changes. For useful supported parallel work, assign bounded, non-overlapping write ownership and inspect outputs. Do not introduce a task store or mandatory parallel implementation.

Scale effort by impact, reversibility, uncertainty and affected users, not size alone; assess operational and data integrity risks; reclassify on new evidence. **Light**: localized, low-impact, easily reversible; focused self-review is allowed. **Standard**: ordinary features/fixes; require independent requirements and standards review plus relevant checks. **Critical**: material harm risks such as access control, payments, destructive migrations or durable data integrity; add applicable risk-specific review and boundary, concurrency, recovery and security checks. For Standard/Critical, state level and evidence-based reason, outcome, scope, constraints and observable criteria in the existing plan or report; connect material results to evidence. No extra file or database is required.

An ADR-worthy decision has meaningful reversal cost or impact, materially different alternatives and rationale future maintainers need. For persisted formats/events, assess old-version reading of new data and rollback; additive changes may still be costly, but apply the same criteria. Reuse an applicable ADR; otherwise, before deciding or dependent implementation obtain independent analyses from at least two distinct native stakeholder subagents, excluding the coordinator. Compare evidence and dissent, decide and write an ADR using project convention or `docs/adr/YYYY-MM-DD-<slug>.md`; include context, alternatives, decision, evidence, consequences and significant risks or dissent. If required analyses or ADR are unavailable, block dependent work; continue independent work. Routine choices need no ADR; don't invent stakeholder preferences or equate agent input with human approval.

Use risk-appropriate feedback per slice. Where useful, test independent expected results at a public boundary; when practical, observe pre-fix failure and rerun afterward. Test-first can help clear contracts; don't write implementation-mirroring tests or unnecessary tests for reversible low-impact edits. Make the smallest change, inspect results and fix failures before proceeding; don't widen scope or overwrite unrelated staged, unstaged or untracked work.

If the coordinator selected an available, permitted execution core and supplied target and capture procedure, use it for the first relevant post-change check when supported; retain or reference its receipt as directed. Observe any needed pre-change failure separately. If core or handoff is unavailable, use permitted checks without bypassing denial, report the receipt gap and don't rerun an unchanged success merely to manufacture one. Standalone Forge needs no other skill or core.

Keep regression assertions within the contract: check public properties for equivalent forms, not incidental bytes or formatting unless exact representation is required. Inspect actual boundary output when a downstream parser or normalizer could conceal a violation.

Reuse passing checks while target and conditions remain valid; rerun for changed state, failure, specific uncertainty or explicit user/host requirements. This doesn't replace required independent review.

After slices, verify integration and the original outcome at a public boundary; examine affected consumers and consequential failures. For behavior changes, run relevant existing automated checks and a proportionate public-boundary check when available, even if not requested. For Standard/Critical, give a separate-context reviewer original requirements, actual target/diff, implementer identity and established separation; identify unknowns. Review and execution are separate completion conditions; another model alone isn't independent review. Address blocking findings and failures within scope; repeat affected review and checks on the changed target. Report failed required criteria/checks as failed and unavailable review/checks as unverified; don't claim completion in either case. Accepted nonblocking minors retain their axis verdict, including fail, with disposition, rationale and residual risk. Never waive unmet criteria or major/critical findings as minor. Verified requires finished independent review without blocking findings and passing required checks and criteria on the current target; it doesn't authorize merge, publish or deploy. If attempts repeat without new evidence or progress, change approach or gather evidence; when blocked, continue independent work and report the blocker without fixed retries or automatic user questions. Only if authorized, make small coherent commits after corresponding checks, excluding unrelated changes. Report actual changes, evidence and material limitations; don't publish or deploy without authorization.

Follow project documentation conventions; create durable records only when useful to work or requested.
