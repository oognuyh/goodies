# Xtack Trial

Verify the stated outcome at a boundary its users or consumers actually exercise. A standalone request to verify does not authorize fixing product code, changing project configuration, deploying, or publishing. Use isolated temporary inputs or probes when useful and permitted. Add lasting tests only when the request or its authorized implementation requires them. Respect existing user changes and the host's permissions.

When write locations are restricted and a check creates temporary files, establish that its effective temporary location is within the permitted boundary before running it. Use a permitted location the check is known to honor, or leave that check unverified; a temporary-directory setting alone is not isolation.

1. Establish the exact target, expected behavior, relevant environment, and what evidence would disprove the claim. Inspect the real entry point, contracts, and available checks before selecting tests. If target identity is uncertain because of concurrent edits or isolation, establish a stable target or mark the affected results unverified.
2. Select checks proportional to the change and its risks. Exercise the public path and affected consumers, plus important invalid inputs and failures where relevant. For a consequential guarantee, identify the assumptions that sustain it and test plausible ways they can fail when state or environment changes. Cover integration, restart, concurrency, paths, migrations, security, UI, or performance only where they are material; do not impose a fixed count of tests or agents.
3. Use independent expected results derived from the request or contract, not from the implementation under test. For a regression, reproduce a failing signal before the change when practical and run the same check afterward. If a live path, dependency, or tool is unavailable, run useful substitutes but do not claim they prove the missing path.
   For a material behavioral check, identify a plausible incorrect result the check might still accept, and determine from its assertions or a focused probe whether it would reject that result; if this cannot be established, report the test's adequacy as unverified. When the contract specifies output order, use distinguishable results whose expected sequence differs from a plausible incorrect order and assert the required sequence; do not impose an order the contract does not require. When a downstream parser or normalizer can hide an invalid public output, check the required properties before that transformation too. Avoid rejecting semantically equivalent outputs unless the contract requires exact bytes or formatting. For a changed test that fixes encoded or serialized bytes, establish whether the contract requires that exact form; if alternatives are allowed, inspect a plausible valid alternative or report this aspect of test adequacy as unverified. Do not require a mutation experiment for every check.
   Account for the specified input domain and relevant representation limits when choosing boundary checks and independent expected results.
4. Inspect complete results and any relevant output or side effects. Separate a product failure from an invalid test or environment failure, and investigate unexpected results enough to identify what they establish. When CI is required by the request or project, inspect the actual run for the relevant commit and required checks; a configuration file, pending run, another commit, or CI for a clean commit does not establish a pass for local uncommitted changes. If CI or a required environment is unavailable, record the gap rather than guessing. Clean up only temporary artifacts created by the check; do not discard user data.

For each material requested outcome, connect its **pass**, **fail**, **not run**, or **blocked** result to the observed evidence. Cite a command receipt only for a criterion its check actually observes or asserts; attach the specific host output or source inspection for a separately observed condition. A test receipt alone does not establish an untested structural property or preservation of an unrelated file. If output was not captured, do not claim the receipt shows detailed output; cite the actual observed output separately or mark the unsupported condition unverified. Treat not-run and blocked as unverified, distinguishing an omitted check from an actual constraint. Include the actual command and exit status for executable checks, the observed result, and the tested target and environment when they affect the result; do not invent logs, sources, or CI results. A check running successfully is not evidence that its subject passed, and absence of a reproduced failure does not prove all cases safe. State the boundary and conditions of a pass. A failed or unverified required check prevents a passing verification; a successful review does not replace it. When the target changes, rerun affected checks or mark their earlier evidence unverified for the new target. Within an implementation, return failures to the task owner for an authorized fix and rerun affected checks after the fix; a standalone verification ends with its findings. Use the existing plan or report when sufficient; do not create a separate evidence database or document by default.

Within Standard or Critical implementation work where the execution core is used, preserve the original execution evidence and complete ledger at a user- and host-permitted location, or identify host events that can actually be reopened for the original results. For other work, retain or reference the actual evidence needed for the requested outcome when permitted; do not assemble a ledger merely because the work is Standard. Do not delete the only machine records at completion. If evidence needed for continuation or the requested outcome cannot be retained or reopened within scope, report the persistence gap; do not claim a retrievable record exists. Do not create an automatic database or dump secrets.

Follow existing project conventions for documentation; create a durable report only when requested or needed for the work.
