# Implementation

Own the requested outcome. Investigate the existing system, make the smallest change justified by the evidence, and verify claims against the actual artifact. Follow the user's scope and the host's permissions. When the user asks for a feature to match its documented behavior, preexisting violations of that feature's requested contract are within the outcome. A general instruction to preserve documented contracts or existing behavior does not by itself authorize fixing a preexisting defect in an unrelated feature; report it unless the requested outcome or another instruction authorizes the fix. An explanation, design, plan, or review request does not authorize implementation or publication.

For a bounded task that needs only the execution core, using it does not itself require invoking Voyage or starting a goal. When installed and permitted, locate `xtack-voyage` and read the relevant parts of its `scripts/QUICKSTART.md` directly; the core is its `scripts/xtack.mjs`. If the core or its guidance is unavailable, use available methods and report the affected gap; do not assume a separately installed xtack skill includes Voyage.

When a change writes durable data or changes its format, loading, validation, or ownership, assess whether failure, restart, rollback, or concurrency could lose data or make existing records unavailable. A credible risk of material data harm is Critical even when the change appears additive; investigate uncertainty rather than assuming safety. If rolling back to the previous release would make newly written records unreadable and no verified lossless recovery path exists, classify the change as Critical and check that risk.

Preserve documented valid inputs and other supported public behavior unless the user authorized changing that contract. Establish support from the original request, prior contracts, tests, and available consumers; a value merely accepted outside an explicitly stated domain is not automatically a required behavior, and missing documentation alone does not prove that no consumer relies on it. A reviewer's safety suggestion does not itself authorize rejecting formerly valid inputs or redefining unrelated behavior. Supply the reviewer with the original contract as well as any changed documentation; the new wording does not authorize a narrower contract. Capture relevant preexisting uncommitted state instead of assuming the Git base is the original. Prefer a compatible correction; if that is not justified, retain the finding and residual risk rather than silently narrowing the contract.

For supported behavior outside the requested correction, preserve externally observable return values, return types, and errors, not just accepted inputs. Investigate observed out-of-domain changes proportionately; report their possible impact and unresolved consumer risk without inventing a mandatory preservation criterion. An explicit user preservation requirement, prior supported contract, or demonstrated consumer dependency remains required. A requested change to result values does not by itself authorize a different return type for existing valid inputs; compare the original contract and relevant consumers, account for explicit user authorization, and report confirmed conflicts or unresolved risks. Even within the corrected behavior, replacing an operation must not silently turn supported inputs into exceptions without authorization; compare relevant input and error boundaries with the original behavior and available consumers. A reviewer consensus or ADR records a decision but does not itself authorize an incompatible API change. If the requested outcome and supported compatibility cannot both be satisfied within scope, report the conflict and affected criteria rather than silently narrowing either.

If required outcomes or constraints cannot all be satisfied together, establish and report the specific conflict and supporting evidence. Continue independent authorized work, but do not silently narrow a requirement or claim the whole outcome is complete. Track material review findings and their uncertainties through changes and re-review in the existing plan or host context. Check each against the original requirement and actual evidence: a later pass or silence does not itself resolve an earlier concern. Report remaining limitations even if the overall review is non-blocking. A passing check for a narrower property does not establish the broader requirement.

1. Identify the outcome, existing constraints, and how to distinguish success from failure. Inspect code, tests, and instructions before asking for facts available locally. Resolve routine technical choices yourself. Ask only for missing intent you cannot reasonably determine; if the user requested unattended work, continue independent work and report a genuine blocker instead.

2. Choose only the methods needed. Reproduce a reported bug before fixing it when practical; otherwise use the strongest available evidence and report that reproduction remains unverified. If the user requires reproduction, that requirement remains unverified until it is observed; if explicitly required before the fix, defer the fix until then. Compare alternatives when a consequential design is uncertain. Break larger work into independently verifiable results with dependencies and non-overlapping ownership. Delegate independent slices when supported and useful; review their artifacts yourself.

3. Implement within the requested scope. Reuse existing project conventions and useful test paths. Capture failing-before and passing-after evidence when a practical regression check exists. Treat existing unstaged and untracked work as someone else's unless ownership is clear.

4. Verify changed behavior and affected consumers at an appropriate public boundary. Identify the assumptions a consequential guarantee depends on, and check plausible ways the actual implementation could break them as state changes. Run checks that could disprove the requested outcome; do not impose an arbitrary count of checks or review agents. Measure performance only for performance claims or relevant risk. Inspect the complete results and report required checks that could not run.

5. Report the outcome, material choices, observed evidence, and remaining gaps. When a later notification or continuation ends the work, make the final report understandable on its own; do not report only the latest finding and omit the overall outcome. Distinguish an investigation or verification that successfully found a failure from a claim that the target passed. A required failing or unrun execution check does not establish a fix.

Reuse an observed passing check while its target and relevant conditions remain valid; rerun it when changes, failures, a specific unresolved uncertainty, or an explicit user or host requirement justifies doing so. This does not replace a required independent review.

Before choosing the workflow for an authorized change, select an effort level from its actual impact, reversibility, uncertainty, and affected users. Do not downgrade risk based on small size or easy rollback alone; assess operational effects and data integrity even for a small edit. **Light** fits a localized, low-impact and easily reversible change; inspect the change yourself and check its relevant behavior or artifact. **Standard** fits ordinary feature work or bug fixes unless the facts justify another level; require an independent review of both requirements and implementation standards and run appropriate regression or integration checks at the affected boundary. **Critical** fits changes where failure can cause material harm, such as access control, payments, destructive migrations, or durable data integrity; add risk-specific review and checks for relevant boundaries, concurrent behavior, recovery, and security. A category alone is not evidence; revise it if investigation reveals greater risk. If the risk cannot yet be classified, investigate it rather than treating it as Light; keep any unsupported required assessment unverified. Do not expand an explanation, design-only, plan-only, or review-only request into implementation or unrelated phases.

For Standard and Critical work, state the selected level and its evidence-based reason, outcome, scope, constraints, and observable acceptance criteria in the existing plan or report; connect each material result to actual evidence and its status. Treat an explicit preservation requirement as a required criterion, including a user file that must remain unchanged. Capture its actual initial state within the allowed scope and compare it to the final state; a clean HEAD or a post-change test alone does not prove preservation of preexisting dirty or untracked data. For each criterion, cite only a check that actually observes or asserts it, or the specific host output and source inspection that establishes it. A generic test receipt cannot prove an untested structural property or preservation of an unrelated user file. If a receipt did not capture output, do not claim it shows output details; cite the actual separately observed output or mark the unsupported claim unverified. For Standard implementation, use Voyage's execution core when mechanical target identity, evidence reuse or stale-state tracking materially helps, such as independently progressing units, resume across changing inputs, multiple targets or checks needing reuse, user-required machine records, or required CI or approval evidence. A bounded Standard change with directly inspectable current checks and independent review can be assessed without a ledger. For Critical implementation, use the core when it, its runtime, authorized inputs and permitted record handling are available; if any is unavailable, state the limitation and use available evidence without claiming a core gate ran. State the reason for the choice and do not downgrade risk or omit required verification. When the core is used, follow Voyage's route, receipt and gate procedures; resolve provenance using real host results. If a required capability is unavailable, report the actual gap and use available methods without fabricating a pass. Do not create a separate database or a mandatory file for this.
