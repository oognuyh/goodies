# Review Evidence

For Standard and Critical implementation where the core is used, leave a retrievable full ledger and its original receipts in a user- and host-permitted location, or report a host event reference that can actually be reopened and contains the relevant original results. Identify the actual file or reopenable event for each retained record; saying only that it is "in this conversation" does not identify a retrievable ledger or receipt. For a retained independent review, or whenever you describe one as retrievable, identify a reopenable event containing it or preserve its output verbatim when permitted; an agent name or generic final-answer label alone does not identify a retrievable event. Compare the reopened output and its attribution with the actual host return for that same reviewer before claiming it is the original; a path or label alone cannot establish the match. Rendered text that looks identical or equal parsed JSON does not establish an exact original; line-oriented writes can add a trailing newline. Do not silently rewrite the review or expand abbreviated hashes and present the result as the reviewer's original output. Label a summary as a summary, and report the gap if the original cannot be retained or reopened. For other work, retain or reference the actual evidence needed for its requested outcome when permitted. Do not delete the only machine records at completion. If permitted durable storage or re-readable host events are unavailable, state the persistence gap without claiming durable evidence. Do not dump secrets or introduce an automatic database.

When a recoverable review is needed and the user and host permit a report file, the independent reviewer may write its own report to a new permitted evidence path outside the reviewed product target and return it through the host. Give that path and permission explicitly; a read-only review request alone does not authorize the write. Check the actual path and applicable boundaries, including links; if its permitted location cannot be established, do not write it. A path check alone is not race-free isolation. Check the actual delegation, target, return and file. Before calling the file the original returned report, compare its contents with the complete returned report body and separately establish attribution from the actual host event; host metadata need not be part of the report body. A path or digest alone cannot prove that match or independence. If it cannot be written, reopened or compared, honor the boundary, label any summary as such and report the actual recovery gap rather than repeatedly reconstructing an original.

Treat review and execution verification as distinct completion conditions for changes. For Standard and Critical work, use a reviewer in a separate context with the original requirements and actual target or diff when the host supports it. Tell the reviewer who implemented the change and how the reviewer context is separate when established; identify unknowns instead of inventing them. Give the reviewer the relevant observed execution results for the current target. When permitted and practical, provide the relevant original output or a reopenable reference and identify the target; label summaries as summaries. Do not create storage or repeat execution solely for the handoff. The reviewer independently assesses the change and may run a check to investigate a specific failure hypothesis or uncertainty; do not repeat an unchanged check merely to duplicate an already observed result. Reading a review skill, self-review, or changing models alone is not independent review. Light work may use a focused self-review. Run the checks relevant to the chosen level and report the actual target, results, and gaps. Address blocking review findings or failed checks within the authorized scope, then repeat the affected review and checks on the changed target. Inspect the returned review’s overall disposition and required axes. Preserve the reviewer’s original verdict. Report the affected requirement as unverified unless separate applicable evidence establishes it; no code findings do not prove unobserved constraints. If a required independent review or check is unavailable, mark it unverified, continue independent work, and do not claim the implementation is complete or verified. An independent review may conclude with an accepted nonblocking minor: keep its original axis verdict, including fail, and report its disposition, rationale, and residual risk. Never waive an unmet required acceptance criterion or a major or critical finding as minor. For Standard and Critical changes, a verified result means the required independent review finished with no unresolved blocking findings and the required acceptance criteria and execution checks passed for the current target; it does not authorize merging, publishing, or deployment beyond the user's scope and host permissions. If attempts repeat without new evidence or progress, change approach or gather missing evidence; when further progress is blocked, continue independent work and report the specific blocker. Do not impose a fixed retry count or automatically ask the user. An investigative task may succeed by establishing a failure without implying that the target passed.

When a gate is used, inspect its assessment and every reason before claiming an implementation is complete. An `unverified` or `blocked` assessment is distinct from an eligible assessment with external provenance still to confirm; resolve the actual risk, criterion, review, CI, or other gap, or report the work as incomplete. Without a gate, do not invent one or treat its absence as a pass; assess the actual evidence and required checks directly. Never remove or downgrade a material risk merely to obtain an eligible result.
