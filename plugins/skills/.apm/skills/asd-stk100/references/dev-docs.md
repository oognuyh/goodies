# 개발 문서 표기와 문서 종류별 규칙

코드·UI 표기와 문서 구성을 판단할 때 해당 절을 읽는다. 문장 표현은 [rules.md](rules.md), 번역투 후보와 예외는 [translationese.md](translationese.md)에서 확인한다. 작업 방식에 따른 정보·구조 보존 범위는 [작업 순서](../SKILL.md#작업-순서)를 따른다.

출처 약칭: 토스 = 토스 테크니컬 라이팅 가이드(technical-writing.dev), 카카오 = 카카오디벨로퍼스 문서 작성 가이드, MS = Microsoft 한국어 스타일 가이드, Google = Google developer documentation style guide. [원문]은 출처의 예, [작성]은 이 스킬이 만든 예다. 예문은 기본 문체인 "~합니다"체로 썼다.

## 1. 문체와 지시문

문체는 [공통 원칙](../SKILL.md#공통-원칙), 지시문은 [문장 규칙 5절](rules.md#5-절차문)을 따른다. 행위자와 주술 호응은 같은 파일의 3.1·4.2·6.6에서 판단한다.

- [원문] 서비스 서버가 카카오 인증 서버로 인가 코드 요청 API를 호출합니다 (카카오).
- 목록 항목과 표 칸은 명사형으로 끝내도 된다. 형식을 맞추는 기준은 [문장 규칙 4.4](rules.md#4-문장)를 따른다.
  - [원문] 액세스 토큰: 사용자 인증, 카카오 API 호출 권한 부여 (카카오)

## 2. 코드 요소

**2.1 코드 서식으로 쓰는 것**
- 식별자(함수, 메서드, 클래스, 변수, 매개변수, 필드), 값, 파일 이름, 경로, 명령어, 설정 키, HTTP 메서드, 상태 코드, 오류 코드, 포트 번호, 패키지 이름 (카카오, Google)
- 오류 문자열과 로그 한 줄도 코드 서식으로 쓴다. 제목 안에서도 같다 (토스).
  - [원문] `NOT_FOUND_USER` 에러를 해결하는 방법

**2.2 조사는 읽는 소리에 맞춘다**
- 코드를 소리 내어 읽었을 때 끝소리에 받침이 있으면 "을, 이, 은, 과, 으로", 없으면 "를, 가, 는, 와, 로"를 쓴다. 받침이 ㄹ이면 "로"를 쓴다.
  - [작성] `config.yaml`을, `main`을, `true`로, `npm`을, `redirect_uri`를, `8080`과
  - 숫자는 우리말로 읽는다. 0(영), 1(일), 3(삼), 6(육), 7(칠), 8(팔)은 받침이 있다.
  - 약어는 글자 이름으로 읽는다. L(엘), M(엠), N(엔), R(알)은 받침이 있다.
  - [원문] `ngrok http 8080`와 같이 → [작성] `ngrok http 8080`과 같이 (토스 문서의 실제 오류)
- 괄호는 건너뛰고 괄호 앞 낱말에 조사를 맞춘다 (카카오엔터프라이즈).
  - [원문] 생성된 URL(Forwarding)를 → [작성] 생성된 Forwarding URL을
- 읽는 법이 갈리면 일반 명사를 붙이거나 조사가 필요 없는 문형으로 바꾼다. "`SQL` 문을"

**2.3 코드를 낱말처럼 굴절하지 않는다**
- 코드에 "하다", "되다"를 붙이지 않는다 (Google).
  - [원문] `nullable` 하지 않았던 필드를 `nullable` 하게 변경 → [작성] null을 허용하지 않던 필드가 null을 허용하도록 변경
- 코드를 직접 가리키고 군더더기 명사를 붙이지 않는다 (카카오).
  - [원문] 나쁜 예 `target_id` 파라미터 값으로 대상을 지정합니다. 좋은 예 `target_id`에 대상을 지정합니다.
- 일반 명사를 붙일 때는 띄어 쓴다.
  - [원문] `failure`필드에 → [작성] `failure` 필드에

**2.4 명령과 코드 블록**
- 명령 앞에 어디서, 무엇을 하려고 실행하는지 쓴다 (토스).
  - [원문] 터미널에서 아래 명령어를 실행하여 React 패키지의 설치 상태를 확인하세요.
- 코드 블록 앞에 그 코드가 하는 일을 쓴다. 코드 뒤에 설명을 몰아 쓰지 않는다 (토스).
- 단계 안 순서는 행동, 명령, 자리표시자 설명, 예상 결과다 (Google).
- 코드 블록에는 언어 이름을 붙인다 (토스).
- 예제는 주어진 명세와 문법을 확인한다. 실행 환경이 없으면 설명용 예시라고 밝히고, 실제로 실행했다고 쓰지 않는다. 문서에 넣을 명령을 운영 환경에서 실행하는 것으로 검증을 대신하지 않는다. 이 항목은 이 스킬의 규칙이다.

## 3. UI 요소와 자리표시자

- 화면의 메뉴, 버튼, 항목 이름은 대괄호로 감싸고 경로는 ">"로 잇는다. "버튼"을 덧붙이지 않는다 (카카오).
  - [원문] 카카오톡의 [설정] > [카카오계정] > [연결된 서비스 관리]에서 동의를 철회할 수 있습니다.
- 코드 안에서 독자가 바꿔야 하는 값은 대문자와 밑줄로 쓰고, 블록 바로 아래에 무엇으로 바꾸는지 적는다 (Google, 카카오는 `${ACCESS_TOKEN}`).
  - [작성] `PROJECT_ID`: 구성원을 조회할 프로젝트의 ID
- 본문에서 조직마다 다른 값을 모르면 "[담당 부서]"처럼 빈자리로 둔다. 코드 자리표시자와 섞지 않는다.
- 값을 모르는 자리표시자 뒤에는 겹조사를 쓴다 (MS).
  - [원문] '%1!s!'을(를) 찾을 수 없습니다.

## 4. 용어

쉬운 말·전문 용어·음차 동사를 고르는 기준은 [문장 규칙 1절](rules.md#1-단어)을 따른다. 여기서는 개발 용어의 표기를 정한다.

- 외래어는 외래어 표기법을 따른다. 업계에서 다른 표기가 훨씬 널리 쓰이면 그 표기를 쓴다 (카카오, 토스).
  - [원문] 어플리케이션 → 애플리케이션, 컨텐츠 → 콘텐츠 (카카오엔터프라이즈) / 프런트엔드 → 프론트엔드 (토스)
- 플랫폼, 언어, 제품 이름은 영문 그대로, 공식 표기와 대소문자대로 쓴다. 비공식 약칭을 쓰지 않는다 (카카오, 토스, MS).
  - [원문] K8을 사용하면 → 쿠버네티스(Kubernetes)를 사용하면 (토스)
- 처음 나오는 낯선 용어와 약어는 괄호에 원어를 쓴다. 그 뒤로는 선택한 용어만 쓴다 (카카오).
  - [원문] SSR(Server-Side Rendering), 클라이언트 시크릿(Client Secret)
- 코드 키워드 자체를 가리킬 때는 `return`처럼 코드 서식으로 쓴다.
- 은어와 직역 동사를 실제 동작으로 쓴다 (토스).
  - [원문] Exception을 던집니다. → 예외(`Exception`)를 일으킵니다. / 서버를 찔러서 → 서버에 요청을 보내서
- 차별 소지가 있는 용어를 바꾼다 (카카오).
  - [원문] 화이트리스트/블랙리스트 → 허용 목록(Allowlist)/차단 목록(Blocklist), 마스터/슬레이브 → 주요(Primary)/보조(Secondary)
- 주요 개념은 용어집으로 관리한다. 동의어 가운데 가장 많이 쓰는 말을 표준으로 정한다 (토스, 카카오).

## 5. 숫자, 단위, 날짜, 버전

- 아라비아 숫자를 쓰고, 네 자리 이상은 세 자리마다 쉼표를 찍는다. "3,000,000건" (카카오)
- 범위는 "이상, 이하, 초과, 미만"으로 쓴다. 연속 범위는 물결표를 쓴다. "1~50", "200~299" (카카오, 토스)
- 기본값과 제한은 괄호에 쓴다. "(기본값: `20`)", "(최소: `1`, 최대: `100`)", "(단위: 초)" (카카오)
- 본문의 절대 날짜와 시각은 국문 단위로 쓴다. "2026년 10월 4일 오후 2시 49분" (카카오). 상대 날짜의 유지·환산 기준은 [작업 순서](../SKILL.md#작업-순서)를 따른다.
- 데이터 형식인 날짜는 형식과 시간대를 밝힌다. "연결된 시각(UTC 기준 RFC 3339 형식)" (카카오), 숫자만 쓰는 날짜는 "2026-10-04" (Google)
- "새로운", "기존", "최신", "이전"처럼 시점에 따라 뜻이 바뀌는 말은 버전이나 날짜와 함께 쓴다 (카카오).
  - [원문] 새로운 사용자 인터페이스는 2.0 이후 버전에서 지원합니다.
- 쌍점은 앞말에 붙이고 뒤를 띄운다. "최대 개수: 99개" (카카오)

## 6. 문서 구조

- 제목 바로 아래에 개요를 둔다. 첫 문장에 문서의 범위와 무엇을 할 수 있는지를 쓰며, 제목을 그대로 되풀이하지 않는다 (토스, 카카오).
- 제목 규칙 (토스, 카카오)
  - 핵심 낱말을 넣고 짧게 쓴다. 물음표와 느낌표를 쓰지 않는다.
  - 개념과 묶음은 명사형, 독자의 행동은 동사형으로 쓴다. 같은 수준의 제목은 같은 형식으로 맞춘다.
  - 단계 제목에는 번호를 붙이고, 고를 수 있는 단계는 "[선택]"으로 표시한다.
- 한 페이지는 한 주제를 다룬다. 같은 내용은 한 곳에만 쓰고 링크로 잇는다 (토스, 카카오).
- 순서가 있는 일은 번호 목록, 나란한 항목은 글머리표, 세 항목 넘게 견주면 표를 쓴다. 단계가 하나뿐이면 번호를 붙이지 않는다 (카카오, Google).
- 보충 설명과 위험 안내의 표기는 [공통 원칙](../SKILL.md#공통-원칙)을 따른다. 필수 지시는 본문이나 단계에 둔다.
- 링크 문구는 대상의 제목으로 쓴다. "여기"를 쓰지 않는다 (카카오).
  - [원문] 바로가기 작성하기를 참고합니다.
- 문서 안의 위치는 "위", "아래"로 가리킨다. 앞 단계를 가리킬 때는 단계 번호를 쓴다 (카카오, 토스).

## 7. 문서 종류별 규칙

**README와 시작하기 (토스의 학습 문서)**
- 첫 문단에 이 도구가 무엇이고 무엇을 할 수 있는지 쓴다.
- 요구 사항 → 설치 → 가장 짧은 사용 예 → 설정 → 문의 순서로 쓴다.
- 각 단계 뒤에 독자가 확인할 결과를 쓴다. 독자가 막힘없이 끝까지 따라 할 수 있어야 한다.

**How-to 가이드와 런북**
- 무엇을 하는 문서인지, 전제 조건, 단계, 완료를 확인하는 방법 순서로 쓴다 (토스).
- 동작·조건·확인 결과를 배치하는 기준은 [문장 규칙 5절](rules.md#5-절차문)을 따른다. 목표가 있으면 먼저 쓴다. "로그를 보려면 `kubectl logs` 명령을 실행합니다." (Google)
- 설정을 빠뜨렸을 때 나오는 결과나 오류 코드를 쓴다 (카카오).
  - [원문] [상태]가 [OFF]인 경우, 카카오 로그인 요청 시 `KOE004` 에러가 발생합니다.

**문제 해결 문서**
- 제목에 오류 문자열을 코드 서식으로 넣는다. 증상, 원인, 해결 방법, 해결 확인 순서로 쓴다 (토스).
- 원인과 현상을 나눠 쓴다. 바로 실행할 명령과 설정을 준다. 버전이나 운영체제에 따라 다르면 그 차이를 쓴다 (토스).

**API·설정 레퍼런스**
- 개요 → 요청(메서드, URL, 인증) → 매개변수 → 응답 → 오류 → 예제 순서로 쓴다 (토스, 카카오).
- 매개변수 표는 "이름 | 타입 | 필수 | 설명" 열을 쓴다. 설명 첫 줄은 무엇인지 정의하고, 조건과 기본값은 그다음에 쓴다 (카카오).
  - [원문] 취소할 금액입니다. 값이 없으면 전액 취소됩니다. (토스페이먼츠)
- 정해진 값만 받으면 값과 뜻을 함께 쓴다. "`NORMAL`(일반결제), `BILLING`(자동결제) 중 하나입니다." (토스페이먼츠)
- 오류 표의 원인 칸은 "~한 경우"로 끝낸다. 해결 방법 칸은 한 표 안에서 같은 형식으로 쓴다 (카카오).
- 주어진 필드·값으로 요청·응답 예시를 만들고, 설명용 값임을 밝힌다. 아직 정해지지 않은 인증·오류는 미정이라고 쓴다.

**오류 메시지 (MS, Google)**
- 무엇이 잘못됐는지와 독자가 할 일을 쓴다.
- 완전한 문장으로 쓰고 마침표를 찍는다. 표준 구문은 "~할 수 없습니다.", "~하지 못했습니다.", "~하는 동안 오류가 발생했습니다."다.

**설명 문서와 설계 문서·ADR**
- 등장 배경과 해결하려는 문제 → 원리 → 다른 방식과 비교 → 사용 사례 순서로 쓴다 (토스의 설명 문서).
- ADR은 상태, 맥락, 결정, 결과, 검토한 대안을 쓴다. 확정된 결정은 첫 문장에 분명하게 쓰고, 제안·검토 단계면 그 상태를 유지한다. 이 항목은 이 스킬의 규칙이다.

**장애 보고서**
- 요약 문단 하나에 무엇이, 언제, 얼마 동안, 왜 일어났고 어떻게 끝났는지 쓴다.
- 경위는 시각과 시간대를 붙인 목록으로, 원인은 시간 순서의 문장으로 쓴다. 사람을 탓하는 표현 대신 시스템과 절차의 문제로 쓴다.
- 재발 방지 항목에는 할 일, 담당, 기한을 쓴다. 정해지지 않은 값은 빈자리로 둔다.
- 이 항목은 국내 IT 기업 공개 가이드에 없어 이 스킬이 정한 규칙이다.

**릴리스 노트와 변경 이력**
- 버전과 날짜를 제목에 쓴다. 변경을 "추가", "변경", "수정", "제거", "지원 중단"처럼 종류별로 묶는다.
- 하위 호환성이 깨지는 변경은 맨 앞에 두고, 영향받는 대상과 독자가 할 일을 쓴다.
- 항목은 명사형으로 끝내도 된다. 이름이 바뀌면 화살표로 쓴다 (카카오 SDK 변경 이력).
  - [원문] 카카오계정 제재 에러명 변경: `ApiErrorCause.BlockedAction` → `ApiErrorCause.BlockedAccount`

**공지**
- 제공된 사실만으로 제목과 본문을 만든다. 시점·대상·영향·독자가 할 일 중 입력에 있는 항목만 담는다. 카카오 데브톡 공지의 구성을 정보량에 맞게 줄인 이 스킬의 규칙이다.
- 점검 일시와 대상만 주어졌으면 그 사실을 알리는 짧은 공지로 마친다. 이용 중단, 사전 저장, 문의처, 사과는 별도로 주어졌을 때만 넣는다.
