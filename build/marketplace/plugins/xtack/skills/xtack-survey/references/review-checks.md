# Detailed review checks

When the change rewrites a contract or its documentation, compare the current behavior against the user's original request and the contract that applied before the change. The rewritten contract is evidence of what changed, not permission to narrow previously valid behavior. Use the actual recorded starting state, including relevant preexisting uncommitted changes; a Git base alone may not contain it. If the original contract cannot be established, mark the affected assessment unverified.

Before reporting a finding from a comparison, verify that each quoted behavior and location is attributed to its actual source, whether baseline or target; check the retrieved path and content again if uncertain.

Check supported unchanged cases for public return values, return types, and errors as well as accepted inputs. Establish support from the user request, prior contracts, tests, and available consumers. A value merely accepted outside an explicitly stated domain is not automatically a required behavior, but missing documentation does not prove that no consumer relies on it; report the observed change, possible impact, and unresolved risk. A requested change to result values does not by itself authorize a different return type for existing valid inputs; compare the original contract and relevant consumers, account for explicit user authorization, and report confirmed conflicts or unresolved risks. When a fix replaces an operation, compare relevant original and new input and error boundaries, including whether supported or demonstrably relied-on inputs now throw; the correction itself does not authorize a silent exception change for them. A reviewer consensus or ADR does not by itself authorize an incompatible API change; distinguish a supported-contract violation from an observed change with unresolved consumer impact.

When a public call signature changes, consider relevant observable metadata and the treatment of arguments previously supplied by callers. Compare the actual contract and available consumers; report a confirmed compatibility impact or unresolved risk without assuming every change is material.

Trace the relevant execution paths and consumers, and run proportionate checks or temporary probes when they can resolve the question. Inspect relevant original execution evidence supplied for the current target; do not repeat the same check solely because the implementer ran it. Run an additional check when it can resolve a specific review doubt, test an independent hypothesis, or recheck a changed target. Assess requirements and implementation standards separately when each is in scope; passing one does not establish the other. For requirements, check the requested outcomes and applicable edge cases against the actual change. For standards, examine relevant design, correctness, type and domain boundaries, security, and maintainability against the project's conventions. If a requested assessment lacks sufficient criteria, mark it unverified; use not applicable when that assessment is outside the requested scope.

Assess whether the relevant evidence can distinguish the required behavior from plausible failures and whether assertions reject valid alternatives. Investigate a concrete gap when it matters: for example, a downstream normalizer can hide an invalid output, an order assertion can miss swapped results, or exact serialized bytes can reject a form the contract allows. Use source inspection or a focused probe as appropriate. A correct implementation alone does not establish test adequacy; if required behavior lacks sufficient evidence, report it as unverified. Do not require a mutation experiment for every review or impose an order or representation the contract does not require.

For relevant input domains and representation limits, assess whether the checks and independent expectations cover material boundaries. If exhaustive checking is required but impractical or unavailable, report the uncovered scope rather than presenting samples as exhaustive proof.
