# Execution core quickstart

Use this when Voyage or a bounded xtack task selects the core for Standard or Light work, or by default for Critical implementation when its runtime, authorized inputs and permitted record handling are available. A bounded Standard change can instead use directly inspectable host checks and independent review without a ledger. Read only the sections needed for the current work. The core requires Node.js, does not invoke host reviewers or authorize actions, and does not automatically persist records. For the complete input shapes, CI, approvals, limits, and troubleshooting, consult [the full reference](README.md), the [gate schema](../references/schemas/gate.schema.json).

For a gate with independent review, supply the actual reviewer overall `disposition` (`non-blocking`, `unverified`, or `blocked`) along with the actual axes, findings, target and routed fingerprints. Missing or malformed disposition leaves a required or supplied review unverified. The gate cannot authenticate the supplied review or its scope.

Set `XTACK_CORE` to the absolute path of this skill's `scripts/xtack.mjs`. For a real task, choose any input and output paths permitted by the user and host. Store records outside the declared hashed target so they do not change it. Decide to use the core before the first relevant post-change check and run that check through the core when it can be expressed as an allowed argument array. This captures the original receipt without repeating an unchanged direct check. Do not fabricate a receipt for an earlier host command. Do not copy secret values into command arguments or persist unreviewed output. The JavaScript demonstration below uses a heredoc, which can create a temporary file outside a restricted write boundary in zsh. The fixed JSON example requires safe serialization and shell quoting for actual task values. When necessary, provide safely quoted input through a pipe or a permitted file instead; neither choice isolates the command.

The gate has one target: each implementation unit's declared paths must be covered by it, and a current receipt or review must identify that exact target. If the requested goal also requires keeping evolving Voyage records or evidence outside the product target, do not add the whole changing record directory to the product target or claim its actual paths are product paths. Use a product-scoped gate for the actual product criteria, and assess the retention requirements separately against the permitted, observable artifacts and any required review. Reconcile both results and gaps against the complete original Voyage goal; a product-only `eligible` gate is not a full-goal gate. If a single machine-evaluated gate for all requirements is explicitly required and cannot be established, report that gap. Do not relabel a receipt's target or treat a host reference as authenticated.

## Assess an existing gate input

For an existing input, verify that its target and any required CI lookup are permitted. Run `node "$XTACK_CORE" gate < "$INPUT"` on the original JSON bytes, inspect the assessment and reasons, and retain the full result when needed. Old v1 ledgers are rejected: preserve them and reconstruct a fresh request from actual evidence instead of retagging. The gate re-snapshots the target and does not authenticate its inputs.

Keep retained artifacts proportional: the full gate result already contains the resumable ledger and original shared receipts, with actual review and preservation evidence retained or referenced where needed. Do not wrap that result with duplicate copies of its input and receipts or create a separate file for every route, request, intermediate gate, receipt or summary merely to record the procedure. Reuse the host's reopenable event references when they contain the original evidence. Avoid Git's administrative directory unless the user directs it: `.git` can be a file, and its contents are not carried into a clone. Choose a permitted, discoverable location outside the hashed target. No particular evidence directory is mandatory.

1. Establish the requested outcome, scope, constraints, risk, and each observable criterion. This is a complete route request; replace its example intent with the actual task:

   ```sh
   printf '%s\n' '{"intent":{"objective":"Fix the filter","scope":{"included":["filter API"],"excluded":[]},"constraints":[],"domain_terms":[],"kind":"bugfix","risk":"standard","risk_reason":"Visible behavior change","criteria":[{"id":"AC1","description":"Combined filters return the correct rows"}]},"risk_factors":["ordinary-change"]}' | node "$XTACK_CORE" route
   ```

   `domain_terms` is an array of `{ "term": "...", "meaning": "..." }` objects, or `[]` if no terms need defining; strings are not valid entries. Supported `risk_factors` are `ordinary-change`, `operational-impact`, `uncertainty`, `reversible`, `access-control`, `payments`, `destructive-migration`, and `durable-data-integrity`. Preserve task-specific risk details in `risk_reason`; do not replace a material risk with an unrelated supported factor merely to pass. Capture the actual result in a permitted location if it will be reused. Use its `fingerprints.intent` for the reviewed intent, `fingerprints.review_context` for the actual reviewed risk context, and `fingerprints.criteria` for each corresponding criterion. Recompute them when the intent or risk factors change. Route output depends on supplied facts and does not discover undisclosed risks. If piping output through another command, use pipefail or check the core process's actual exit code; a successful `tee` does not make a failed route pass.

2. Choose the actual target root and all relevant paths, including the project contract documents used to derive the criteria, changed and untracked inputs, and protected files needed for explicit preservation criteria. If a relevant contract cannot be included, establish its identity separately from actual host evidence or leave the affected assessment unverified. Inclusion in a target does not authorize editing a file. A JSON request to `node "$XTACK_CORE" run` is sent on stdin. Capture the allowed initial state of protected files before changes. The request contains `target: {root, paths}`, `cwd`, `argv`, and `timeout_ms`; the complete example below constructs this request directly. `argv` is an argument array, not shell code. Optional `output_limit_bytes` is an integer from 0 to 65536 for each of stdout and stderr; 0, the default, records byte counts only.

   If an original host event cannot be reopened and permitted files are needed across tool calls, capture core stdout directly rather than retyping it later. For a check, the optional `node "$XTACK_CORE" run --receipt "$NEW_RECEIPT" < "$REQUEST"` reserves a new file outside the declared target before the child runs and returns the same receipt on stdout. Use a different new path for every run, including reruns; never overwrite an earlier receipt. Inspect any retained file and actual error before retrying: a failed capture or stdout may follow an executed command. For snapshots, or an older core without this option, use the [direct-capture example](README.md#capture-original-output), which handles exclusive creation and incomplete snapshots. Do not silently retry an ambiguous invocation. If neither permitted storage nor a genuinely reopenable event is available, report the gap. Run the relevant check and retain its original receipt in a permitted location or a re-readable host event.

   Read the receipt's status, exit code, signal, target identities, process group observation, and any actually captured output. CLI exit 0 means a receipt was produced; it does not mean the command or criterion passed. A current successful receipt with a `present_or_reused` or `unknown` process group observation is not eligible execution evidence; the overall gate also depends on other evidence and required conditions. A complete captured output whose UTF-8 text is shorter than its declared raw byte count is also unverified as positive evidence; compare it with the original host output. This is only a narrow inconsistency check, not authentication. Even `absent` is only a point-in-time observation and cannot detect escaped descendants. A timed-out receipt's `cleanup` is also unverified: establish process state before retrying work with effects. Preserve the original receipt, including these fields; do not remove them to change a gate result. A missing process group observation retains its previous treatment, but an untagged snapshot identity is still unverified; Windows reports `unsupported` for process group observation. Consult the full reference for limitations. If the target or relevant conditions change, rerun affected checks. For an unchanged target and conditions, reuse the retained receipt instead of rerunning the check to reconstruct it.

   For required preservation, compare the original machine-generated baseline directly with the final observation; do not retype hashes into another record. When using a snapshot and the execution target also includes files to be changed, capture the protected paths separately so their before/after identities remain directly comparable; reuse equivalent existing evidence when available. For example, where supported, a retained `sha256sum` baseline can check file contents from the same working directory against the same paths, but does not establish file modes. Alternatively, compare complete core `snapshot` results programmatically using the recognized `snapshot_algorithm` `xtack-snapshot-v4` on both, the same canonical root and exact returned path spellings, and matching digests; see the [comparison procedure](README.md#compare-protected-snapshots). A snapshot digest includes path and metadata as well as content; it is not the raw SHA-256 of an individual file, even for a single-file target. Untagged or unrecognized snapshots do not establish preservation under the current algorithm. Mode semantics vary by platform; ownership, ACLs, extended attributes and file capabilities are not covered. Neither approach captures Git's index or proves transient changes absent: inspect the original and final staged and unstaged state separately when the request requires it. If the baseline cannot be retained or recovered within scope, report the gap.

   If core use was selected only after a direct host check, that original result can support a criterion through its actual host reference, but it is not a core receipt. The current gate requires a successful current-target core receipt for its required execution and Critical risk checks. Capture a still-needed, relevant execution with `run` when permitted; if none is available, leave the gate unverified and report why rather than inventing a receipt or rerunning an unchanged check solely to manufacture one.

3. Build the gate input from the actual intent, target, current `risk_factors`, implementation units, criterion evidence, and required review. Pass the factors used for routing to the gate too; update them if the actual risk facts change. A unit records its result, affected paths and boundaries, dependencies, and the criterion IDs it must satisfy. IDs may include preservation obligations: linking one does not mean that its protected file is modified. Link a cross-unit invariant to the relevant units and check it at final integration. For Standard or Critical work, the review must be performed in a separate context and identify the current target, intent fingerprint, `review_context_fingerprint`, and observed reviewer/implementer separation. Before a final integration review, route the exact intent, criteria and risks that the gate will evaluate and give those facts and returned fingerprints to the reviewer, together with the original goal and any separately assessed requirements. A product-scoped gate's fingerprints differ from a full-goal route when their intents differ; do not substitute one for the other. A single review can cover integration and the full goal when its actual scope and target support both, but establish each binding from what it actually reviewed. Supply the reviewer with the original requirements, actual target or diff, scope, declared risk factors, and relevant execution results. Include relevant units and dependencies when they matter: the review-context fingerprint does not bind them. A changed risk context requires review of the current risks; an older review lacking the binding remains unverified unless its actual context can be established. Do not attach a newly computed value to an old review without establishing what it covered. They may investigate a concrete failure hypothesis or uncertainty; do not require a duplicate run merely to repeat an observed check. Keep review and execution as separate conditions.

   For each supplied finding declared `resolved`, provide `resolution_evidence` for its resolution, separate from the original finding's `evidence`. Reuse a relevant existing review or check when it supports the resolution. Missing, blank, or explicitly unknown resolution evidence is unverified, including in an older retained ledger; add actual evidence before reevaluating. The gate cannot authenticate the evidence or detect omitted findings.

   For a shared command result, put the actual receipt once in `receipts` under an ID and give each applicable evidence item its `criterion_id`, `criterion_fingerprint`, `receipt_ref`, and observed `assertion`. A direct `receipt` is also supported; do not supply both in one item. Use an actual host output or source-inspection `reference` and `target_identity` for a separately observed criterion. A test receipt belongs only to criteria that test actually observes or asserts: it does not by itself prove untested source structure or an unrelated user's file was preserved. If the receipt did not capture output, do not claim it shows detailed results; cite the observed original host output separately. Mark unsupported outcomes unverified. Confirm the host references can really be reopened; do not invent them.

   The following `gate` demonstration uses one receipt for two criteria and declares one implementation unit. It hashes this core file and checks the installed Node runtime; it is **not evidence for the user's task**. It deliberately supplies no review, so its Standard gate remains `unverified` even if both criteria pass. Run it only if useful and permitted.

   ```sh
   node - "$XTACK_CORE" <<'JS'
   const path = require('node:path');
   const { execFileSync } = require('node:child_process');
   const core = path.resolve(process.argv[2]);
   const root = path.dirname(core);
   const call = (op, input) => JSON.parse(execFileSync(process.execPath, [core, op], {
     input: JSON.stringify(input), encoding: 'utf8'
   }));
   const target = { root, paths: [path.basename(core)] };
   const intent = {
     objective: 'Demonstrate two checks of the Node version',
     scope: { included: ['Node version output'], excluded: [] },
     constraints: [], domain_terms: [], kind: 'bugfix', risk: 'standard',
     risk_reason: 'Demonstration of a standard change',
     criteria: [
       { id: 'VERSION', description: 'Output has version syntax' },
       { id: 'MAJOR', description: 'Major version is at least 24' }
     ]
   };
   const route = call('route', { intent });
   const receipt = call('run', {
     target, cwd: root, argv: [process.execPath, '--version'],
     timeout_ms: 5000, output_limit_bytes: 256
   });
   const match = /^v(\d+)\.\d+\.\d+\s*$/.exec(receipt.stdout.text || '');
   const checks = { VERSION: !!match, MAJOR: !!match && Number(match[1]) >= 24 };
   const input = {
     intent, target, receipts: { 'node-version': receipt },
     evidence: intent.criteria.map(c => ({
       criterion_id: c.id, criterion_fingerprint: route.fingerprints.criteria[c.id],
       receipt_ref: 'node-version', assertion: {
         status: receipt.status === 'success' && checks[c.id] ? 'pass' : 'unverified',
         rationale: 'Evaluated the actual version output.'
       }
     })),
     implementation: { units: [{ id: 'version-check', outcome: 'Demonstrate checks',
       paths: target.paths, affected_boundaries: ['Node version'], depends_on: [],
       criterion_ids: intent.criteria.map(c => c.id) }] }
   };
   process.stdout.write(JSON.stringify(call('gate', input)) + '\n');
   JS
   ```

   For real work, replace the demonstration with the actual intent, target, observations and units. Add a review only from the actual independent reviewer response: its requirements and standards results, findings, target identity, and the intent and review-context fingerprints supplied for that review. Identify a reopenable original response and evidence of reviewer independence. Do not attach fresh fingerprints to an older review without establishing what it covered. For new Standard/Critical work use `gate` and pass the actual overall `review.disposition`; do not infer it from the axis results. Neither version authenticates the report or reconciles the actual review's scope and unresolved assessments against the full request; do not turn passing axes into a claimed overall pass. If an applicable review leaves a required criterion unverified and no other applicable evidence resolves it, include a separate evidence item with that criterion’s fingerprint, `assertion.status: "unverified"`, and a reference to the actual review. Bind a target identity only when the review’s actual target is established; otherwise omit it. The gate excludes evidence bound to a known older target from the current assessment but retains it in the ledger; a criterion covering an earlier period can remain unverified after the target changes; assess that gap separately and do not rebind historical evidence to a new target. Once separate applicable evidence independently establishes that the specific gap is resolved, preserve or reference the earlier ledger and review when permitted, and omit or replace the resolved uncertainty in the new evaluation input with the applicable resolution; do not erase history or omit an unresolved gap merely to pass. The gate cannot authenticate these claims; if review or provenance is unavailable, retain the gap as unverified.

4. For a new Standard/Critical task, send the fresh full gate input on stdin to `node "$XTACK_CORE" gate` and retain the **full** result when permitted. The result's `ledger` includes the contracts, original receipts and references. Use its existing result without repeating an unchanged evaluation. If reevaluation is needed and a compact view is useful, first preserve the full result or the full input and all its referenced receipts, then pass that retained JSON on stdin to the matching versioned command, for example `node "$XTACK_CORE" gate --compact` for v2.

   The matching `gate --compact` **reevaluates** the input: it hashes the current target and rechecks required CI, so changed conditions can produce a different result. Compact output omits the ledger and cannot by itself be used to resume or reevaluate. A missing receipt reference, conflicting inline receipt/reference, or invalid ID is an error. The core checks the supplied records and target but cannot establish that a test proves its assertion or authenticate host or review provenance. Do not treat `eligible` or a candidate state as an authenticated pass or permission to ship. Inspect original host results and follow host permissions. Reuse a gate result only while its target, criteria, review, CI, approval, and other relevant inputs remain valid; otherwise reevaluate affected conditions.

5. After retaining the full gate result, inspect the records created for this run and decide the references the final report needs. If an unreferenced intermediate's actual content is already included in that retained result, remove that redundant file only when permitted. When referring to embedded evidence, identify the retained file and its actual location in the ledger; do not break an existing or promised file reference. Keep original review output, unique or uncertain records, earlier-target evidence needed for the work, preexisting files, and distinct before/after observations even if their contents match. A listing made before the gate was saved cannot establish which later files are redundant.

For a requested fix or implementation, an `assessment` of `unverified` or `blocked` prevents completion until its actual reasons are resolved; do not mistake it for an eligible assessment whose separate `verification` field only needs host provenance confirmation. An investigation or verification can itself finish by accurately reporting a failed target. Inspect unknown risk factors, every required criterion, implementation, review, CI, and limits. Preserve material risks rather than deleting them to pass.

For Standard and Critical work, leave a full ledger with original receipts in a user- and host-permitted retrievable location, or report actual host event references that can be reopened. Do not delete the only machine records after completion. If scope or host capabilities prevent either form of retention, report the persistence gap without claiming a durable record exists. Do not create an automatic database or dump secrets.

Identify the actual file or reopenable event for each retained record. For a retained independent review, preserve the reviewer's actual output verbatim or reference a reopenable event containing it; an agent name or generic final-answer label is not a retrievable event. Do not silently rewrite the review or expand abbreviated hashes and present the result as the original. Label a summary as a summary and report the gap if the original cannot be retained or reopened.
