# Voyage goal store

`voyage-goal.mjs` uses Node.js and accepts one UTF-8 JSON object on stdin; malformed UTF-8 is rejected before any goal operation. Set `VOYAGE_STORE` to its installed absolute path. Choose a **new goal directory** in a permitted location, with an existing parent directory. The field is named `file` for the CLI, but its value is the goal directory, not a JSON file. The store publishes a separate record for each revision. It cannot schedule a turn, enforce host permissions, authenticate the contents, or prove that a recorded check supports the outcome.

The input and each record are limited to 4 MiB. Current stores stop reading as soon as the limit is exceeded, so a pipe producer can see a broken pipe; check the store's actual error and exit status. Older stores read all input before rejecting it. An input exactly at the limit still needs EOF before it can be accepted.

Run `node "$VOYAGE_STORE" --help` for a brief text summary without stdin. `-h` and `create`, `show`, or `update` followed by `--help` or `-h` also show this summary; `show` and `update` add command-specific details. Help writes text to stdout and exits successfully; operation results and errors remain JSON. Some older versions do not support help; the immediately preceding version supports these invocations but not command-specific details.

The store rejects extra arguments to an operation. Current versions add a stdin and help hint to that JSON error without echoing argument contents; older versions return the shorter error. Consumers should not depend on exact error-message text.

All goal text fields can retain supplied content, and the store does not enforce a user's content exclusions. If a user excludes material from the goal and the write cannot be shown to respect that restriction, do not create or update a free-text record through that workflow. Agent instructions or an intention to omit content are not an effective independent control. Continue permitted work in session state; assess any permitted recovery alternatives and report gaps. This does not prevent host transcripts, tool logs, or other write paths from retaining material. Do not silently delete or rewrite existing history.

## Create and recover

Replace the example path, original request, constraints, and criteria with the real ones.

Create the parent directory if needed, but leave the goal directory itself absent: for `file: "/permitted/path/filter-goal"`, `/permitted/path` must exist and `filter-goal` must not. Never delete or reuse an existing goal directory to make creation succeed. When saving CLI output and running subsequent commands, check the store's actual exit status before treating the record as created or updated. In zsh, `status` is read-only; use a different variable such as `rc` if capturing `$?`. If a wrapper fails after the store ran, use `show` to establish the observed revision before retrying an update. The shell examples use fixed JSON literals; serialize and shell-quote actual task values safely rather than inserting arbitrary text into those literals.

```sh
# Replace this with the actual installed script path. Set it before invoking Node:
VOYAGE_STORE="/absolute/path/to/xtack-voyage/scripts/voyage-goal.mjs"
printf '%s\n' '{
  "file": "/permitted/path/filter-goal",
  "original_request": "Fix the filter",
  "constraints": ["Preserve existing filters"],
  "criteria": [
    {"id": "AC1", "description": "Combined filters work", "status": "pending", "evidence_ids": []}
  ],
  "units": [
    {"id": "U1", "outcome": "Identify the failure", "status": "pending", "criterion_ids": [], "depends_on": []},
    {"id": "U2", "outcome": "Correct and verify filtering", "status": "pending", "criterion_ids": ["AC1"], "depends_on": ["U1"]}
  ],
  "evidence": []
}' | node "$VOYAGE_STORE" create
```

The returned `record` has a `goal_id`, revision and `active` status. `original_request` and `original_constraints` preserve the initial request and constraints. Current constraints may change only with actual user steering supplied in that update; the record retains constraint history. Preserve exclusions and operational boundaries as part of the actual request or constraints, and do not invent steering.

If the user and host permit those path details in the returned output and its retention, `create`, `show`, and `update` accept `"include_locator": true`. A successful response then includes `locator.file`, exactly as supplied, and, for a relative file, `locator.cwd`, the process working directory. The response's record supplies the ID and revision. Use both parts as a recovery hint; for a relative file, run the store with the exact file string under the recorded cwd. Do not lexically normalize `..`: a preceding symlink can make it address another directory. Recheck the directory and any independently observed ID and revision. On Windows, locator requests reject drive-relative and current-drive-rooted paths before writing; use a fully qualified or ordinary relative path. Default operations are unaffected. Paths can move or be replaced, and neither the locator nor the record authenticates the goal. The locator is not written into goal revisions and does not ensure that a response can be reopened after interruption. Older stores reject this option; inspect the actual error and use an allowed original input event or other known path if available. Omit the option if its output or retention would violate a restriction.

The `file` string cannot contain unpaired UTF-16 surrogates; a host could otherwise resolve a different U+FFFD path. Valid Unicode paths and goal text remain supported. On POSIX, a relative `file` with `include_locator: true` is rejected before the goal operation if the actual working-directory bytes cannot be verified or represented faithfully as the returned `cwd`; a relative operation without a locator or an absolute locator does not require that cwd. Windows cwd behavior has not been independently verified. Do not automatically normalize an older ambiguous locator to another path: use a permitted actual path and an independently observed ID and revision when available, or report identity continuity unverified.

The store checks the original JSON number spelling for `minimum_revision` and `expected_revision`, and for `version`, `revision`, `previous.revision`, and constraint-history revisions in every stored revision. A number that would be rounded by JSON parsing is rejected before use. Mathematically exact decimal or exponent spellings are accepted subject to the existing integer and range rules. An older executable can silently accept such rounded input or records; rolling back loses this check. A record that an older executable accepted may now be unreadable: preserve the original bytes and history for manual investigation rather than rewriting them. Earlier canonicalization can already have lost the original value and cannot be detected from the rewritten number. This check does not authenticate a goal or its history.

To resume, identify the intended directory explicitly. Do not search for or select the newest goal by assumption. If the goal ID and revision were previously observed from a separate reliable source, pass them as `goal_id` and `minimum_revision`; this example uses revision `1` because creation just returned it. Substitute the actual observed ID and revision, and omit either field when that anchor is unavailable. A mismatched ID or older revision is rejected before the record is returned.

```sh
printf '%s\n' '{"file":"/permitted/path/filter-goal","goal_id":"REPLACE-WITH-PREVIOUSLY-OBSERVED-ID","minimum_revision":1}' | node "$VOYAGE_STORE" show
```

Older versions of this script reject the optional `goal_id` field on `show`. If using a known older version, omit it and compare the returned ID against the independent anchor before relying on the record. Do not retry without the ID merely because an otherwise current script reports an identity conflict or another error.

When an earlier `completed` record has a criterion without an identified reference, `show` adds `completion_warnings` with code `unidentified_references` and the affected `criterion_ids`. The record and exit status are unchanged; inspect and reassess those claims. Normal responses omit this field, and older executables do not report it. Its absence does not establish evidence accessibility, authenticity, sufficiency, or recoverability. Affected responses have an additional top-level field, which consumers that enforce an exact key set must allow.

If storage is forbidden, hardlinks are unsupported, Node is unavailable, or the record cannot be created or read, continue authorized work using session state and report that durable recovery is not assured. Do not overwrite or silently migrate a prior single-file record, unsupported version, corrupt or incomplete history. Do not automatically remove temporary artifacts or empty goal directories: inspect and recover explicitly within the user's permissions. A failed or interrupted write may have produced artifacts or published a revision; inspect the identified goal before retrying.

Earlier store versions could check one directory but read or write another when an input path included a symlink followed by `..`. If such a path was used, inspect the actual affected goals and independently observed IDs before relying on prior results. The current store preserves path components when appending record filenames; it is not a race-free boundary against concurrent path replacement.

Where Node exposes a nonblocking open flag, revision reads and directory synchronization use it to avoid waiting for a writer if a checked path is replaced by a FIFO, as observed on Linux. The flag is omitted where unavailable; it does not make all device or filesystem operations nonblocking or prevent parent-directory races. After linking a revision, the store checks its identity against the temporary file it wrote; an identity mismatch is an error and may leave a published path for inspection. The goal-directory sync compares the opened directory and the path after sync with the directory checked before publication; a detected mismatch reports unverified durability. Temporary-file cleanup checks the directory and file identities before unlinking. These checks are not atomic path guarantees. A revision may already have been published after an error or when durability is unverified, so inspect the actual identified goal before retrying.

The store rejects a goal directory that is itself a symlink, including when its path ends in separators or `.` components. Earlier versions could accept those suffixes; use the intended non-symlink goal path and verify its identity. Intermediate symlinks and concurrent path changes remain outside this check's guarantees.

## Update and complete

Use the `goal_id` and current `revision` returned by `create` or `show`. When recovering, compare the returned ID with any independently observed ID for the intended goal before updating; if they differ, do not update the returned record as that goal. Without a prior ID, identity continuity is unverified. Matching IDs do not authenticate a record. This example uses placeholders; replace the ID and revision with values actually returned. Every update must use the current revision. If a concurrent update wins, inspect the explicitly identified goal and reconcile the changes rather than overwrite them.

```sh
printf '%s\n' '{
  "file": "/permitted/path/filter-goal",
  "goal_id": "REPLACE-WITH-ACTUAL-ID",
  "expected_revision": 1,
  "changes": {"status": "blocked"}
}' | node "$VOYAGE_STORE" update
```

`changes` may supply `constraints`, `criteria`, `units`, `evidence`, or `status`; supplied arrays replace their prior values, so retain all applicable entries. Optional `steering` is an actual later instruction from the user, not an agent inference. Changing current constraints requires `steering` in the same update. A criterion has `id`, `description`, `status` (`pending`, `met`, `unmet`, or `unverified`) and `evidence_ids`. A unit has `id`, `outcome`, `status` (`pending`, `in_progress`, or `completed`), `criterion_ids`, and `depends_on`, an array of other unit IDs that must be completed first. Dependencies must exist and be acyclic; use an empty array when there are none. Evidence has `id`, `description`, and `reference` to an actual observation.

For an active or blocked goal, dependency validation checks the recorded prerequisite unit status, not whether its linked criteria are met or its evidence is sufficient. Changing a criterion's status alone does not automatically reset linked units. A criterion can span several units, so an incomplete shared criterion does not necessarily mean every contributing unit is incomplete. Assess the prerequisite's actual outcome and supporting evidence before starting dependent work; the stored status does not establish that check or enforce edit order.

When only adding evidence, retain the existing evidence entries and existing criterion links, and append new entries and any relevant links. Rewording evidence already used by a `met` or `unmet` criterion triggers reassessment; change it when the underlying observation or requirement actually changed, and do not hide conflicting evidence to avoid reassessment. Current stores compare evidence field values, so changing only JSON object key order does not trigger reassessment. Older stores may treat that reorder as a change, including after a rollback; this does not change the v2 record format.

When a completion update would require reassessment, newer stores append the triggering categories (`steering`, `definitions`, and/or `referenced evidence`) to the existing error message. These categories reveal which kinds of change were supplied, but do not identify affected criteria or prove whether old evidence remains applicable. Exact error-message text therefore differs from older stores. Inspect the prior and proposed records and the actual evidence before reassessing; adding a new evidence entry alone is not a referenced-evidence change.

Record progress and results in statuses and evidence; do not rewrite `outcome` or criterion `description` merely to report completion. Those fields define the work, and changing them triggers reassessment of existing completion claims. Refine definitions when needed or update them when the requirements or work change. If separating a criterion because different parts need different evidence, preserve every original required part in the resulting criteria and link actual evidence where available; leave unsupported parts unverified. Compare the revised criteria against the original request and constraints before completion. Splitting the change and completion into separate updates does not establish that omitted requirements were met.

For reassessment, the store treats each unit's unique `criterion_ids` and `depends_on` as link sets: changing only the order within either array does not invalidate claims. It preserves the supplied order in the record but does not assign priority or execution order to it. Adding or removing a link still triggers reassessment; the order of the top-level criteria and units remains significant. Older stores can reassess even on a link permutation. The absence of automatic reassessment is not proof that evidence remains valid after external changes.

When a definition, referenced evidence or actual steering change triggers reassessment, the current store can accept an existing unit that retains its previously started or completed status while a prerequisite is now incomplete, such as when a new prerequisite is added. It resets that dependent to `pending` before publishing; inspect the returned units and reassess their actual evidence before restarting them. A newly started unit or a newly completed unit with an incomplete prerequisite is still rejected. If the update does not trigger reassessment, explicitly set affected started or completed dependants to `pending` when moving a prerequisite back to `pending` or `in_progress`. Older stores require the explicit reset even when reassessment will otherwise occur.

The goal status is `active`, `blocked`, or `completed`. For a valid non-completion update that triggers reassessment, the store resets every resulting `met` or `unmet` criterion, including inherited criteria, to `unverified` and clears its evidence links. Started dependent units return to `pending`, and completed units without dependencies return to `in_progress`; inspect the returned record and reassess, including claims that may still be supported. A completion update requiring reassessment is rejected without publishing a revision. An invalidated `unmet` becomes `unverified`, not `met`, and reassessment does not itself change a blocked goal to active. Reassessment itself does not remove entries from the submitted evidence array; earlier revisions retain evidence later replaced or removed by the caller. Older executables may leave stale `unmet` claims in place; inspect their actual definitions and evidence on recovery. Completion requires nonempty criteria and units, every criterion marked `met` with evidence, and completed units linked to the criteria or necessary dependencies. For a new completion, each criterion must link at least one evidence reference other than the exact placeholders `unknown`, `unverified`, `not known`, `not verified`, `not available`, or `n/a` (case-insensitive, ignoring surrounding whitespace). Other unknown evidence can remain recorded. This check does not establish that an identified reference exists, is accessible, or is true. Earlier completed v2 records remain readable without automatically applying this newer check; inspect their claims before relying on them. After reopening one, a new completion must satisfy the check. Older executables do not enforce it. The coordinator must independently inspect the actual current evidence and compare it with the original request and applicable steering before marking the goal completed. Reopen a completed goal explicitly before making subsequent changes. Completion is not permission to ship.

If an explicit action prohibition has no corresponding criterion, add the missing requirement even when compliance is unverified rather than a proven violation. Preserve the prior revision as the source of previous evidence links, and retain the existing criteria and evidence; reopen a completed goal as `blocked` or `active` in the same update. Add the missing criterion and its appropriate unit link together, so a later link change does not trigger another reassessment. Adding the criterion triggers reassessment: inspect the returned record and, in a subsequent update, restore only criteria and units supported by reassessed prior evidence. In that subsequent update, record a proven violation as `unmet`; when coverage is insufficient to establish compliance, leave the new criterion `unverified` and the goal open. Other evidence may remain applicable, but the absence of a contradiction alone does not establish that it is valid. Do not invent user steering or claim completion while a requirement is unmet or unverified.

Assess a retention criterion against the actual retained record and evidence before completing the goal; a still-`pending` status alone does not establish that those artifacts are absent. If the criterion and all other completion conditions are supported, and that update does not require reassessment from steering, changed definitions or changed evidence on previously met or unmet criteria, their statuses and the goal's completion can be recorded in the same update. An existing record alone does not prove accessibility or provenance. If the user requires access to the final revision or recovery in a separate session, a pre-completion record alone does not establish that outcome. If verifying that exact completed revision is itself a prerequisite for creating it, report the circular dependency and use an authorized external verification record if it actually satisfies the request; otherwise leave the requirement unverified. A planned later write, action, or report is not evidence that it has already happened; do not mark a finding resolved or claim a completed artifact solely on that plan.

Both execution core gate versions evaluate one exact target; an evolving goal directory can have a different identity from the product checked by a retained receipt. When one gate cannot faithfully cover both, use the [separate product and retention assessment](QUICKSTART.md) and reconcile all actual goal criteria and required reviews here. Do not claim a product-scoped gate establishes retained goal artifacts, or rewrite a unit's actual affected paths to make it pass. An explicitly required single machine-evaluated full-goal gate remains a gap if it cannot be established.

Reassessment does not automatically require rerunning every check. Inspect retained evidence and its actual sources and confirm that the target, relevant requirements, and execution conditions still support each claim; earlier revisions preserve earlier entries when permitted and available. Reconnect evidence that remains applicable and restore the corresponding unit or criterion only after that assessment. Rerun affected checks or leave the claim unverified when applicability cannot be established.

For a multi-unit goal, keep the previously observed revision before an update that can trigger reassessment. Afterward, the earlier revision can identify the former criterion-to-evidence links; read the identified revision and actual evidence within the permitted scope, then assess whether each still applies to the current target and conditions. Once assessed, compatible criteria and units can be restored together in one update, and the goal can be completed in that update if all completion conditions hold and it introduces no further reassessment-triggering changes. Preserve dependency order and leave unsupported claims unverified. Reusing an ID or prior status alone is not evidence that a result is still valid.

Removing or replacing an evidence ID on a criterion that remains `met` or `unmet` triggers reassessment, including when the replacement evidence already exists. Changing an evidence object previously referenced by either verdict also triggers it. Reordering IDs or adding an ID while retaining existing ones does not trigger it; the coordinator must still check the added evidence for relevance and conflicts. After reassessment, connecting evidence to an `unverified` criterion and marking it `met` or `unmet` is allowed. The store does not verify the evidence itself. Older executables do not enforce the same reassessment for `unmet` criteria.

Successful operations return `record`, `authenticity: "unverified"`, and `history_completeness: "unverified"`; write results also report `durability`, which can be `unverified` if directory synchronization is unavailable. Failed operations return a nonzero status and a JSON error; do not treat them as saved progress. Each revision retains its own contents, potentially including sensitive data: minimize retained details and account for the entire history when applying retention or deletion. Exclusive publication protects against replacing an existing revision; it does not prevent external modification or deletion of history. The hash chain detects some inconsistencies but does not authenticate the records. Without an independent anchor, removal or modification of the last revision may leave a plausible shorter or altered history. `minimum_revision` detects a result older than a previously observed number, but cannot authenticate contents or detect replacement at that same revision. History completeness remains unverified; do not claim that `show` established the latest revision is intact.
