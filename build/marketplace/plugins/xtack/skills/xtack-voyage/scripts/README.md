# Xtack execution core

`xtack.mjs` provides deterministic routing and evidence assistance for tasks executed through a host, including Voyage goals. It requires Node.js and uses only built-in modules. This script does not store Voyage goals, invoke host agent tools, authenticate arbitrary JSON, enforce all host actions, or authorize deployment. The caller must follow host permissions. Run `node /path/to/xtack.mjs --help` for the entry points.

Every command takes one UTF-8 JSON object from stdin and prints one JSON object to stdout. Malformed UTF-8 is rejected before a requested operation runs. Invalid input or an unavailable target root returns exit 2 and a JSON error on stderr. A successfully captured command that fails, times out, or cannot start is still a successful CLI invocation: inspect the receipt's `status`, `exit_code`, `signal`, and `error` rather than the CLI exit code. CI collection needs Git, an authenticated `gh` and network access. Git commands can run locally configured filters, whose side effects are not controlled by the core. Nothing is stored automatically.

The examples use `$XTACK` for the absolute path of `scripts/xtack.mjs` and `/workspace/project` as the actual target root; replace both. They use fabricated task and host-reference values to show the shapes, not actual evidence. The JSON shell examples use fixed literals; safely serialize and shell-quote actual values instead of inserting arbitrary text into them. The JavaScript heredoc examples can create temporary files outside a restricted write boundary in zsh; when necessary, use safely quoted input through a pipe or a permitted file. These methods do not isolate the command.

## Route

```sh
printf '%s\n' '{
  "intent": {
    "objective": "Correct the incident filter",
    "scope": {"included": ["incident list API"], "excluded": ["deployment"]},
    "constraints": ["preserve existing filters"],
    "domain_terms": [{"term": "resolved", "meaning": "incident lifecycle status"}],
    "kind": "bugfix", "risk": "standard", "risk_reason": "Visible filtering behavior",
    "criteria": [{"id": "AC1", "description": "Combined filters return the correct incidents", "required": true}]
  },
  "risk_factors": ["ordinary-change"]
}' | node "$XTACK" route
```

The kind is `bugfix`, `feature`, `refactor`, or `investigate`; risk is `light`, `standard`, `critical`, or `unknown`. The result gives the suggested playbook, risk level, review/execution needs, and `fingerprints` for the entire intent, each criterion, and the review risk context. The `playbook` entries are candidate specialists, not mandatory calls; use the actual task and `requirements` to select methods. In particular, Light does not require an independent reviewer unless the user or host does, while Standard and Critical implementation changes require independent review and relevant execution checks. An investigation does not automatically require either through routing; apply the user's request and the actual evidence needs. The `sha256-canonical-json-v2` intent and criterion fingerprints sort object keys recursively, preserve array order, and treat omitted criterion `required` as `true`. They use separate `xtack-intent-v2` and `xtack-criterion-v2` domains. The core rejects an intent when an original JSON number would change its decimal value during parsing or become non-finite; equivalent decimal spellings and negative zero retain their canonical value. This check cannot recover a number already rounded by the caller before it supplied JSON. Earlier v1 bindings do not match v2: preserve existing ledgers and original evidence, then re-establish the actual intent, applicable evidence and review before recording fresh bindings. A retained ledger that itself contains a lossy or non-finite intent number is rejected during input validation, rather than returned as a stale assessment; preserve it and recover the actual intent separately. Older installed core scripts still use their own algorithm; update each installed copy when adopting v2. The separate `sha256-xtack-review-context-v1` fingerprint binds that intent fingerprint, effective risk and exact factor strings after deduplication and JavaScript's default string sort; omitted factors equal `[]`, and unknown factors are included. Use the returned values rather than inventing them; they identify declarations but do not authenticate their source. Explicit `ordinary-change` raises Light to Standard; `access-control`, `payments`, `destructive-migration`, or `durable-data-integrity` raises the level to Critical. Unknown factors and `unknown` risk remain unverified at the gate. Actual risk classification and the sufficiency of the playbook remain the caller's responsibility.

## Capture a command and target

```sh
printf '%s\n' '{
  "target": {"root": "/workspace/project", "paths": ["src", "test"]},
  "cwd": "/workspace/project",
  "argv": ["node", "--test"],
  "timeout_ms": 30000
}' | node "$XTACK" run
```

`argv` is executed directly with `shell: false`, in `cwd` inside the target root. `timeout_ms` is required for this individual command and must be an integer from 1 through 2,147,483,647; it is not a model-session deadline. Values above Node's safe timer range are rejected before launch. Older core versions and receipt schemas accept at most 3,600,000 ms, so they reject a longer run request and do not recognize its receipt as current execution evidence; assess actual older-reader gate results and retain the original receipt when rolling back. The runner reports the actual exit code or signal, timeout/spawn error, duration, and the platform, architecture and Node version. It hashes every regular file and directory in the declared paths before and after execution, including untracked and ignored files there; `.git` metadata is excluded. It detects target symlinks and reports an incomplete identity for a symlink, unreadable/missing input, unsupported file type, or detected concurrent snapshot change. Paths escaping the root are rejected. Filesystem checks are not a race-free security boundary against concurrent malicious path replacement. An unchanged digest covers only the declared paths and snapshots; it cannot prove that other files, network services, or transient modifications did not affect the command.

Before running a child, the core also checks the original JSON number tokens for `timeout_ms` and `output_limit_bytes`. A number that would round or underflow during parsing is rejected, even if its parsed value appears to be an allowed integer; equivalent integer spellings such as `1e3` remain supported. Older cores can accept such requests, and their receipts record only the parsed values, so those receipts cannot reconstruct the original numeric tokens.

Where Node exposes nonblocking and no-follow open flags, snapshot uses them when opening a checked regular file. This avoids waiting for a writer if that file is replaced by a FIFO in the observed Linux case and rejects a final-component symlink. Flags unavailable on a host are omitted. This does not prevent parent-directory races, guarantee that all device or filesystem operations are nonblocking, or make `timeout_ms` a deadline for the snapshots themselves.

Arguments containing unpaired UTF-16 surrogates are rejected before launch: a child may otherwise receive a replacement character instead of the supplied argument. Valid Unicode pairs and an explicitly supplied U+FFFD are accepted. Older cores can accept such arguments, and their receipts remain readable, but this core will not treat a receipt containing an unpaired surrogate in `argv` as positive execution evidence; explicit failures retain their existing handling. An affected receipt can keep its criterion unverified even if another passing receipt is present. Reassess affected historical evidence without rewriting it.

Only byte counts are reported for stdout/stderr by default. To include bounded output in the returned JSON, set `output_limit_bytes` to 1–65536; the limit applies to each stream. Output, arguments, paths, and host references can contain secrets. Do not put secrets in `argv` or preserve command output without checking it. The runner does not dump environment variables, and the user chooses if and where to retain the JSON. Save selected records **outside the hashed target**: writing a receipt inside a declared directory changes the target and invalidates earlier evidence.

The timeout bounds waiting for the direct process and its output pipes. On POSIX the runner attempts to signal its process group only while the leader has not been observed to exit; on Windows it attempts to signal the direct child. If the leader closes before escalation, the delayed signal is not sent. A numeric process-group ID is not a stable handle, and the leader can exit between the check and signal. The optional `cleanup` object records signal attempts and failures as `unverified`: successful signal delivery, leader exit or pipe closure does not prove that same-group or escaped descendants stopped. A command that started and reached its deadline is `timed_out` even if cleanup signaling fails; inspect `cleanup` before retrying potentially effectful work. Output pipes can be cut off, and `exit_code`/`signal` can be unknown. Old receipts without `cleanup` remain readable but do not establish cleanup. Descendants may write after the final snapshot, so an unchanged snapshot alone does not establish a stable target. Follow host cleanup policy and use actual host isolation or supervision when required.

Use `snapshot` with `{"target":{"root":"/workspace/project","paths":["src","test"]}}` to obtain the current identity without executing a command. `snapshot` does not accept `--compact`; that option is only for `gate`. Neither a zero exit code nor a snapshot proves an acceptance criterion by itself.

Current snapshots carry `snapshot_algorithm: "xtack-snapshot-v4"` and include each observed regular file and directory's permission and special mode bits (`0o7777`) as reported by the host. They preserve the supplied relative target path spellings and check their components before resolving them; `file` and `./file` are distinct identities. A normal in-root `dir/../file` remains supported when the traversed directory is accessible, but symlinks or missing or non-directory traversal components make the snapshot incomplete. Paths that temporarily leave the root or contain a `.git` component are rejected. An incomplete snapshot does not stop `run` from executing its requested command, but cannot establish current positive evidence. Platform and filesystem mode semantics differ; Windows may not support POSIX special bits. The snapshot does not cover ownership, ACLs, extended attributes, file capabilities, transient changes or state outside its declared paths. Check those separately when required. Filesystem traversal and change checks are observations, not a race-free isolation boundary.

For each visited directory, v4 compares raw entry bytes and marks the snapshot incomplete if an entry cannot be decoded as valid UTF-8; it does not rename or hash that entry through a replacement-character alias. Explicit target roots, target paths and run working directories containing unpaired UTF-16 surrogates are rejected before resolution. Valid Unicode, including U+FFFD and a leading U+FEFF, remains supported. Arbitrary POSIX filename bytes cannot be represented by this JSON interface. Windows filename fidelity and raw-listing behavior require native verification; these checks are not a race-free filesystem boundary.

Existing v3, v2 and untagged snapshots, receipts, reviews, approvals and ledgers remain readable, but their target identity is unknown to the current core; they cannot establish current execution evidence, reviews, failures or approvals. v3 could miss invalid UTF-8 directory entries, and v2 normalized paths before checking them; neither can establish the current identity under v4. Only the exact string `xtack-snapshot-v4` is recognized. Other values, including malformed values, remain structurally readable for compatibility and are assessed as unknown. Preserve those records without inventing an algorithm; obtain new observations or reviews when permitted and necessary. Older executables do not understand v4 and can still evaluate old identities under weaker rules. The new digest uses a separate domain from older snapshots so honest old and new digests differ, but no identifier or digest authenticates its source or makes an older executable understand future algorithms.

If an older ledger itself supplies a target root or path with an unpaired surrogate, the current gate rejects that input with exit 2 rather than returning an `unverified` assessment or a ledger. Preserve the original, independently establish a permitted actual target, and use available authorized observations for a new assessment; do not normalize the path to U+FFFD or retag historical evidence.

At runner completion, new receipts include `process_group_observation`. On POSIX, a read-only signal-zero probe reports `absent`, `present_or_reused`, or `unknown`; it does not terminate anything or authenticate group ownership. A group can appear present because of a surviving child, a zombie or a reused ID. A success receipt with `present_or_reused`, `unknown`, or a malformed observation is not eligible execution evidence. The gate's per-evidence `process_group_status` exposes the observation, `invalid`, or `not_recorded`; the original receipt remains authoritative for its recorded details. `absent` is a point-in-time observation and cannot rule out escaped descendants or later writes. On Windows the value is `unsupported` and the gate retains the prior direct-child behavior; it does not establish descendant termination. A missing observation retains its prior treatment, but an untagged snapshot identity is still unverified. A missing field can also result from accidental loss or editing, and older gates ignore it, so the field is not a fail-closed guarantee or an authenticated record.

For each referenced positive receipt, the gate also checks a narrow complete-output contradiction: when `text` is a string and `truncated` is `false`, its UTF-8 encoded length cannot be smaller than the reported original `bytes`. Such evidence becomes unverified and its observation reports `output_status: inconsistent`; compare the retained record with the original host output. Invalid UTF-8 bytes can decode to replacement characters that take more bytes to re-encode, so equality is not required. Count-only records, missing optional fields, truncated output and unreferenced receipt-table entries retain their prior behavior; explicit failure assertions keep their existing priority. Older v1 receipts remain readable but an affected positive assessment can change on reevaluation. This check misses equal-length changes, altered counts or omitted fields and does not authenticate output, a reviewer or an assertion.

## Capture original output

If an original host event cannot be reopened and permitted files are needed across tool calls, capture the core's stdout directly at the first execution instead of retyping it later. For `run`, set `XTACK_CORE` to the absolute core path (`$XTACK` in the earlier examples), `XTACK_REQUEST` to the actual request JSON file, and `XTACK_RECORD` to a **new** path in an existing trusted, permitted directory outside every declared target path:

```sh
node "$XTACK_CORE" run --receipt "$XTACK_RECORD" < "$XTACK_REQUEST"
```

The option validates the run request and exclusively reserves the destination before starting the child. An existing file or final symlink is a conflict; it is not overwritten and the child is not started. On success, the file and stdout contain the same receipt bytes; as with plain `run`, a failed child can still produce a receipt and a successful CLI exit. Use a different new path for each execution, including a rerun, and keep earlier referenced receipts. Paths are resolved from the invoking process's working directory; the parent must already exist. If the declared target covers every permitted destination, use an actual reopenable host event or report the retention gap.

After a reservation, a failure can leave an empty or partial new file; preserve and inspect it. An error saying the command may have run does not establish whether it did. If capture fails after the runner finishes, stdout may contain the receipt; if stdout delivery fails after capture, inspect the saved receipt. If both fail, inspect whatever original evidence is actually available. Do not automatically remove the file or rerun an ambiguously completed command merely to recreate evidence. Error messages cannot guarantee that stderr or stdout reached a closed consumer.

Exclusive creation prevents overwriting an existing final pathname at reservation time; it does not prevent parent-directory replacement, same-user races or later modification or deletion. The path and file checks are not a sandbox or authentication. No file or directory fsync is performed, so successful capture does not establish durability after a crash or power loss. The caller can still use plain `run`, a different writer or an older core without this protection. Older cores reject `--receipt`; check the installed core's capabilities before use and do not silently retry an ambiguous failed invocation.

For `snapshot`, or for a known older core, the following direct-capture example is an alternative. Set `XTACK_OP` to `run` or `snapshot` and use the same request and new-record variables as above. Store bounded output only when the user and host allow it; the default run request captures byte counts without output text. This Node example creates the destination exclusively and writes the original stdout bytes:

```sh
node - "$XTACK_CORE" "$XTACK_OP" "$XTACK_REQUEST" "$XTACK_RECORD" <<'JS'
const fs = require('node:fs'), path = require('node:path'), {spawnSync} = require('node:child_process');
const [core, op, request, record] = process.argv.slice(2);
if (!['run', 'snapshot'].includes(op)) throw Error('Expected run or snapshot');
const input = fs.readFileSync(request), fd = fs.openSync(record, 'wx+', 0o600);
try {
  const p = spawnSync(process.execPath, [core, op], {input, stdio: ['pipe', fd, 'inherit']});
  if (p.error || p.signal || p.status !== 0) throw p.error || Error('Core invocation failed');
  const size = fs.fstatSync(fd).size;
  if (size > 16 * 1024 * 1024) throw Error('Output saved but too large for this example to validate');
  const raw = Buffer.alloc(size);
  for (let at = 0; at < size;) { const n = fs.readSync(fd, raw, at, size - at, at); if (!n) throw Error('Short read'); at += n; }
  const r = JSON.parse(raw.toString('utf8'));
  if (op === 'snapshot' && !(r && r.snapshot_algorithm === 'xtack-snapshot-v4' && r.complete === true && typeof r.root === 'string' && path.isAbsolute(r.root) && Array.isArray(r.paths) && r.paths.length && r.paths.every(p => typeof p === 'string' && p.trim()) && Number.isSafeInteger(r.files) && r.files >= 0 && Array.isArray(r.issues) && !r.issues.length && typeof r.digest === 'string' && /^[0-9a-f]{64}$/.test(r.digest))) throw Error('Snapshot incomplete, malformed, or uses an unrecognized algorithm');
  if (op === 'run' && !(r && r.target_before?.snapshot_algorithm === 'xtack-snapshot-v4' && r.target_after?.snapshot_algorithm === r.target_before.snapshot_algorithm)) throw Error('Receipt snapshots use an unrecognized or mismatched algorithm');
  console.log(JSON.stringify(op === 'run' ? {status:r.status, exit_code:r.exit_code, signal:r.signal, error:r.error, target_unchanged:r.target_unchanged} : {snapshot_algorithm:r.snapshot_algorithm, complete:r.complete, root:r.root, paths:r.paths}));
} finally { fs.closeSync(fd); }
JS
```

A failed or unvalidated capture can leave a new file that is not yet evidence. The core command may already have run, and output exceeding this example's validation limit remains in the file; inspect it when permitted rather than repeating a check merely to reconstruct a receipt. For a protected-state baseline, run this with `snapshot` **before editing**, confirm the returned root and paths are the intended protected target, and stop before edits if capture or confirmation fails. Never use an older file after a failed capture. Capture the final snapshot with the same request and a different new path; compare the original JSON observations as shown in the [protected-snapshot comparison](#compare-protected-snapshots). For the gate, read the original receipt JSON as shown in its [gate example](#evaluate-and-retain-a-ledger); do not transcribe its fields. A successful core invocation produces a receipt but does not mean its command passed. Count-only capture does not expose detailed child output; if details are required but not actually observed, report that gap. For captured output, inspect its truncation flag. The saved files are not authenticated and do not establish Git index or transient state.

## Compare protected snapshots

When preservation is required, capture the protected paths before editing and again afterward using the same root and paths, with the original machine output retained or available from reopenable host events. If a needed baseline capture fails or is incomplete, do not start a change that depends on it or substitute an older record. Confirm that the observed paths are the intended protected target. For permitted files, the [direct-capture example](#capture-original-output) shows exclusive creation; a failed capture can leave an empty or partial file that is not evidence.

The following compares two actual saved `snapshot` JSON observations without transcribing digests. Run it only after the before capture succeeded and its target was confirmed. Pass the original before and after paths:

```sh
node - "$BEFORE" "$AFTER" <<'JS'
const fs = require('node:fs'), path = require('node:path');
const valid = r => r && r.snapshot_algorithm === 'xtack-snapshot-v4' && r.complete === true && typeof r.root === 'string' && path.isAbsolute(r.root) && Array.isArray(r.paths) && r.paths.length && r.paths.every(p => typeof p === 'string' && p.trim()) && Number.isSafeInteger(r.files) && r.files >= 0 && Array.isArray(r.issues) && !r.issues.length && typeof r.digest === 'string' && /^[0-9a-f]{64}$/.test(r.digest);
let a, b;
try { [a, b] = process.argv.slice(2).map(p => JSON.parse(fs.readFileSync(p, 'utf8'))); }
catch { console.log(JSON.stringify({comparison:'unverified'})); process.exit(1); }
const same = valid(a) && valid(b) && a.snapshot_algorithm === b.snapshot_algorithm && a.root === b.root && JSON.stringify(a.paths) === JSON.stringify(b.paths);
const comparison = !same ? 'unverified' : a.digest === b.digest ? 'matching' : 'different';
console.log(JSON.stringify({comparison}));
if (comparison !== 'matching') process.exitCode = 1;
JS
```

The result covers only declared paths at observed times, not Git's index, transient changes or record authenticity. A separate later command cannot enforce that an earlier failed capture was honored. If no permitted record or genuinely reopenable host event exists, report the gap rather than reconstructing a baseline.

## Gate: overall review disposition

For workflows requiring independent review, supply the reviewer's actual `requirements`, `standards`, findings, target, fingerprints and overall `disposition` (`non-blocking`, `unverified`, or `blocked`). A missing or malformed disposition is unverified; a current-target and current-intent blocked disposition blocks. The [gate schema](../references/schemas/gate.schema.json) permits incomplete review input to be preserved; the [review schema](../references/schemas/review.schema.json) describes a complete review. The gate does not authenticate supplied evidence.

```sh
node "$XTACK" gate < "$INPUT"
```

A full result contains an `xtack-ledger-v2` ledger in an `xtack-core-v2` envelope. Pass the ledger, `{ "ledger": <ledger> }`, or the full result to `gate` for reevaluation. `--compact` omits the resumable ledger. Each evaluation re-snapshots the target and may inspect Git or query CI. The old v1 gate and its records are not supported; preserve old records and re-establish intent, evidence and review from actual sources before submitting a fresh request. Do not simply retag a record.

## Evaluate and retain a ledger

`gate` consumes an intent, target, evidence, and, for a change, an implementation contract. Each implementation unit names its result, paths, affected boundaries, dependencies on other units, and the criterion IDs it must satisfy. These may include preservation obligations: linking a protected file's criterion does not imply modifying it. Unit paths must be covered by the declared target. A final ledger records supplied units and evidence; it does not establish that units were planned before implementation or verified before other edits. Inspect actual host events when that order matters. Compare an allowed initial file state to the final state when preservation is required; a post-change test or clean HEAD alone cannot establish preservation of preexisting dirty or untracked data. This supports decomposition of a large goal into units.

`route` and `gate` reserve the `xtack-ledger-` namespace and accept `xtack-ledger-v2`; the gate also accepts `xtack-core-v2` envelopes. Other reserved versions, including v1 ledgers, are rejected. Unversioned fresh requests remain supported.

The following is a `gate` example. It constructs a gate input using a previously captured receipt at a location **chosen by the caller**. The reviewer and host references are examples; replace them only with the actual host output after independently checking it. The example reuses `receipt.target_after` as the review identity only for the case where host or reviewer evidence independently establishes that the reviewer inspected that exact target. A receipt alone does not establish what the reviewer saw; if the review target cannot be established, keep the review unverified.

```sh
node - /tmp/chosen-receipt.json /workspace/project "$XTACK" <<'JS' | node "$XTACK" gate
const fs = require('node:fs');
const { execFileSync } = require('node:child_process');
const receipt = JSON.parse(fs.readFileSync(process.argv[2], 'utf8'));
const root = process.argv[3];
const core = process.argv[4];
const intent = {
  objective: 'Correct the incident filter',
  scope: { included: ['incident list API'], excluded: ['deployment'] },
  constraints: ['preserve existing filters'], domain_terms: [],
  kind: 'bugfix', risk: 'standard', risk_reason: 'Visible filtering behavior',
  criteria: [
    { id: 'AC1', description: 'Combined filters return the correct incidents' },
    { id: 'AC2', description: 'Neighboring filter combinations remain correct' }
  ]
};
const risk_factors = ['ordinary-change'];
const { fingerprints } = JSON.parse(execFileSync(process.execPath, [core, 'route'],
  { input: JSON.stringify({ intent, risk_factors }), encoding: 'utf8' }));
console.log(JSON.stringify({
  intent, risk_factors, target: { root, paths: ['src', 'test'] },
  implementation: { units: [{ id: 'U1', outcome: 'Correct filters', paths: ['src', 'test'],
    affected_boundaries: ['incident list API'], depends_on: [], criterion_ids: ['AC1', 'AC2'] }] },
  receipts: { 'tests-1': receipt },
  evidence: [
    { criterion_id: 'AC1', criterion_fingerprint: fingerprints.criteria.AC1, receipt_ref: 'tests-1',
      assertion: { status: 'pass', rationale: 'Replace with the observed combined-filter assertion.' } },
    { criterion_id: 'AC2', criterion_fingerprint: fingerprints.criteria.AC2, receipt_ref: 'tests-1',
      assertion: { status: 'pass', rationale: 'Replace with the observed neighboring-filter assertion.' } }
  ],
  review: { disposition: 'non-blocking', requirements: 'pass', standards: 'pass', target_identity: receipt.target_after,
    intent_fingerprint: fingerprints.intent,
    review_context_fingerprint: fingerprints.review_context,
    reference: 'host://actual-review-result',
    independence: { status: 'confirmed', reference: 'host://actual-separate-review',
      reviewer: 'actual-reviewer-id', implementer: 'actual-implementer-id' } }
}));
JS
```

Each evidence item has a criterion ID, its `criterion_fingerprint`, a distinct assertion (`pass`, `fail`, `not_run`, `blocked`, or `unverified`) and either a command receipt or a reference. As shown above, an optional `receipts` map can retain each original receipt once; each relevant criterion refers to it with `receipt_ref`. Receipt IDs are ledger-local identifiers, not paths: use 1–128 ASCII letters, digits, `.`, `_`, or `-`, beginning with a letter or digit; `constructor`, `prototype`, and `__proto__` are forbidden. An unknown reference, unsafe ID, or supplying both `receipt` and `receipt_ref` in one item is an input error (exit 2). Existing inline `receipt` items remain supported and can coexist with referenced items in the same ledger.

The gate compares the original JSON numeric tokens for each supplied receipt's `duration_ms`, `timeout_ms`, `exit_code`, `stdout.bytes` and `stderr.bytes` with their parsed values. Equivalent decimal spellings are accepted; a lossy, nonfinite or unavailable numeric source cannot establish a pass or failure. Independently observed current failures retain their blocking precedence. Full result ledgers retain the parsed receipt objects unchanged and carry a separate `receipt_precision` sidecar, with value- and location-bound claims for inline and table receipts, including unused entries. JSON serialization can emit rounded numeric values in place of the original input tokens; it cannot reconstruct those tokens, so preserve the original input separately when needed. With the sidecar consistently retained, a lossy value remains unverified on replay. A previously versioned ledger without a valid claim remains readable but its receipt precision is unverified; a fresh direct receipt can be assessed from its current input. Moving an inline receipt, renaming a table entry, or reordering a receipt's object keys invalidates its serialized-value binding and leaves it unverified. A copy at a genuinely new location can inherit precision only from an identical receipt with a valid existing claim still present in the same ledger, with exact current tokens and no conflicting claims. The sidecar retains occupied receipt locations. Removing an inventoried receipt or its claim, changing a receipt so its prior claim no longer matches, or supplying a claim for a location absent from an available inventory, makes the inventory permanently incomplete in later results and disables this inference; an unavailable or malformed inventory does likewise. The inference cannot prove that identical parsed copies had identical original tokens. Preserve original evidence and do not recreate a claim to bypass uncertainty. These claims are consistency markers, not signatures: they cannot authenticate receipts or recover digits rounded before the core received them. Older core versions may ignore the sidecar and optimistically assess affected receipts after rollback. Compact output does not include a resumable ledger.

Only attach a receipt to criteria the command actually checks. Sharing a receipt does not prove that all assertions are related or true; retain and inspect the actual host results and any separate source observations. For a reference without a receipt, add `target_identity` from `snapshot` for the observed target. A pass assertion needs its rationale; a successful command alone is insufficient. Exact trimmed, case-insensitive `unknown`, `unverified`, `not known`, `not verified`, `not available`, and `n/a` pass rationales are unverified, including for required execution and Critical risk coverage. Substantive explanations containing those words remain allowed. Affected passes may become unverified when reevaluated. Independently established current failures retain their blocking precedence; the new placeholder rule does not change fail assertions. An execution failure or interruption is reported as such and does not automatically establish a product failure. A modification requires a structurally valid, successful, current-target receipt attached to at least one **required** criterion. Missing assertions, failed or unavailable checks, incomplete target identity, or a changed target do not pass the gate. Intent and evidence schemas are under `../references/schemas/`.

For Standard and Critical changes, provide requirements and standards review results, `target_identity` from the actual current target, `intent_fingerprint` and `review_context_fingerprint` from the route used for the actual review, the review result reference, and the implementer/reviewer identities and host evidence reference for their separation. The gate treats identities that differ only in surrounding whitespace as the same; distinct strings still do not prove separate people or contexts. Supply the reviewer with the declared risks and relevant execution results. If risk factors change, obtain review of the current risks before using their new context. A digest alone does not identify a checkout: the recognized snapshot algorithm, root, declared paths and digest must match. Findings include severity, disposition, location, violated criterion, evidence, impact, and confidence. Use an explicit `unknown` value where the review could not determine a detail. A critical/major unresolved finding or failed requirement blocks. A minor finding can be accepted within the caller's delegated scope if rationale and residual risk are recorded; a failed standards axis remains visible.

For reference-only criterion evidence, review result references, required independent-review references and identities, and approved-delivery references, the exact placeholders `unknown`, `unverified`, `not known`, `not verified`, `not available`, and `n/a` (case-insensitive, ignoring surrounding whitespace) are treated as missing. A reference-only failure with no identified observation is unverified, while a separately established failure or denied approval still blocks. A valid receipt is assessed on its own even if an accompanying reference is unknown. Finding details retain their existing rules, and substantive descriptions may contain uncertainty. This does not authenticate any reference, identity, or approval.

An otherwise eligible supplied review, including an optional review, is unverified if `review_context_fingerprint` is missing, malformed or differs from the current route's context. Reviews without this field are unverified. Do not silently add a new fingerprint to a historical review: establish its actual target and risk context or obtain a current review. A context mismatch does not suppress an existing blocking finding on the same target and intent; existing stale-target and stale-intent handling remains unchanged. This check cannot authenticate reviewer provenance, prove the reviewer saw the risks or coverage, detect omitted factors, or bind changes to a coverage mapping. Older core versions ignore the field and retain the weaker behavior.

For an accepted minor, a missing or blank `rationale` or `residual_risk`, or an exact `unknown`, `unverified`, `not known`, `not verified`, `not available`, or `n/a` placeholder (case-insensitive, ignoring surrounding whitespace), leaves an otherwise eligible review unverified. Existing independently blocking conditions retain their precedence. A substantive description can include uncertainty; the gate cannot judge whether its content is sufficient or true. Do not invent a rationale or risk to restore eligibility.

When `standards` is `fail`, the current accepted-minor exception requires every supplied finding to be an accepted minor. For example, an otherwise valid current-target, current-intent review with a complete accepted minor with nonempty acceptance details alongside an evidenced resolved major is blocked: the format does not connect the failed axis to specific findings, so the gate cannot establish that the remaining failure concerns only accepted minors. Incomplete findings or blank acceptance details can instead be unverified. Obtain an actual review of the current target and use its real axis verdict and findings; do not omit or relabel findings merely to obtain eligibility.

For each finding declared `resolved`, provide `resolution_evidence` describing or referencing the actual evidence supporting resolution. The finding's `evidence` may describe only the original defect. A missing or blank value, or the explicit placeholders `unknown`, `unverified`, `not known`, `not verified`, `not available`, and `n/a` (case-insensitive), makes an otherwise eligible review unverified; an established blocker retains precedence. An existing host review or check can be referenced; inspect it against the current target and requirements because the gate cannot authenticate or assess its content. Supply actual evidence before reevaluation; do not invent it. The gate cannot discover findings omitted from its input.

Critical changes additionally require `risk_coverage` mapping each stated critical risk factor to a required criterion backed by a current successful execution receipt, for example `[{"factor":"access-control","criterion_id":"AC1","rationale":"Exercises the protected boundary"}]`. If Critical was selected without a named critical factor, use `critical-general`. Each factor needs at least one mapping with a substantive rationale and evidence for that **same** required criterion: its current fingerprint, a passing assertion, and a current successful receipt that passes the output consistency check. Exact, trimmed, case-insensitive `unknown`, `unverified`, `not known`, `not verified`, `not available`, and `n/a` rationale values are treated as missing; a substantive explanation that contains those words is not rejected merely for containing them. If several mappings are supplied for a factor, the gate considers all of them and reports one qualifying criterion ID; coverage status does not depend on their order. Actual required-criterion and review failures retain their existing blocking precedence, as does an applicable denied approval for delivery.

Retained records preserve their input fields. Reevaluation can change `eligible` to `unverified` when the only rationale is a recognized placeholder, or `unverified` to `eligible` when a later supplied mapping satisfies all the conditions. No evidence is fabricated or rerun. A mapping and receipt are caller-supplied claims: conditional eligibility does not establish that the check covers the risk, authenticate its result or provenance, prove independent review, or grant permission. Inspect the actual host evidence and the risk before acting.

The gate emits a `ledger` containing the original contracts, references, receipts and any supplied limits. You may retain it at an explicitly chosen location and later pass the **whole returned gate JSON** or `{ "ledger": <ledger> }` back to `gate`. Each evaluation hashes the current target again and fetches required CI again. An observation from a known older target or older criterion remains in the ledger with `target_status` or `criterion_status` set to `stale`, but does not determine the current outcome; a current valid result is still required. A failed observation whose target or criterion is unknown is `unverified`, not a confirmed current failure or silently discarded. Reviews of changed targets or intents require re-review. A host-observed direct check can be cited as criterion evidence, but it is not a core receipt and cannot alone satisfy the gate's required execution or Critical risk checks. If no relevant core receipt exists, those conditions remain unverified; do not invent one or repeat an unchanged check solely to reconstruct a receipt. The ledger may contain sensitive arguments, optional captured output, and references; protect it accordingly. It is neither tamper-proof nor an authenticated record.

Criterion evidence is bound to the individual criterion and target, not the rest of the intent or the implementation units. Changing the objective, scope, constraints, domain terms or unit outcomes while leaving a criterion and target unchanged can therefore leave its old evidence structurally eligible. The review context binds the intent and declared risks, but not the implementation units. When these declarations change, assess whether the original evidence and review still cover the actual work; obtain updated evidence or review when affected. An eligible gate cannot make that judgment.

For a concise response, use `node "$XTACK" gate --compact < "$XTACK_GATE_INPUT"` (or supply a previously retained full gate result). It performs the same evaluation, including a fresh target snapshot and required CI query, then returns `view: "compact"`, `ledger_included: false`, `resumable: false`, and the assessment details without the complete ledger. Compact output is not a resumable ledger: retain the input with its receipt map, or the full gate result, in an explicitly permitted location when continuation needs it. Re-evaluation may differ if the target or CI state changed. The default `gate` output remains the full ledger.

`assessment` and `delivery_eligibility` are `eligible`, `unverified`, or `blocked` based on the **supplied** records. `candidate_state` is a conditional workflow hint (`draft`, `in_review`, `changes_requested`, `verification_failed`, `verification_pending`, `approval_required`, `budget_exhausted`, `verified`, or `ready_to_ship`). It never asserts host authority. The separate `verification` and `ready_to_ship` values stay `unverified` unless there is a blocking failure because this process cannot authenticate the supplied records. The coordinator may make an actual goal-completion decision only after examining the host's original tool results and review context, resolving the outstanding evidence gaps, and respecting host permissions. A host approval or publish permission is not implied by an eligible gate.

The gate's `limitations` also identifies an unknown declared risk, unrecognized risk factors, an incomplete target snapshot, and missing required execution evidence when present. These messages can coexist with a blocking result; inspect the individual criteria, review, limits, CI and approval results as well. Both full and compact output include them. They do not establish the authenticity or sufficiency of supplied evidence.

## CI, approvals, and explicit budgets

To require CI, pass e.g. `"ci":{"required":true,"repo":"owner/repo","run_id":123,"required_jobs":["test"]}`. The core queries the requested GitHub run via `gh run view`; checks the run ID, GitHub URL, origin repository, HEAD SHA, completion and required jobs; nonstandard origin ports, control or whitespace characters, query/fragment delimiters, and unnormalized paths that do not identify the standard GitHub repository leave CI unverified, as do nonstandard HTTPS ports in the run URL; checks the whole worktree for tracked/untracked changes and the declared target for ignored files; and rechecks the target, Git state and origin after collection. It also checks the entire repository's index for `assume-unchanged` or `skip-worktree` entries before and after the query, because those flags can hide changed files from Git status. Any such entry makes CI unverified even when its file is unchanged; sparse checkouts commonly use these flags. Git errors, timeouts or oversized output also leave CI unverified. The core never clears the flags. An unavailable tool, authentication, job, network, dirty workspace, or mismatched target is unverified. A completed failing run or required job is blocked when it can be associated with the assessed target; otherwise its result remains unverified. Ignored inputs outside the declared target, nested submodule indexes and unobserved or transient changes may still affect a run. `required_jobs` is caller-supplied, not a discovered branch policy; the local executable and remote service remain trust boundaries. Numeric `run_id` values must be positive safe integers whose original JSON token is mathematically exact; use a positive decimal string for a larger ID. The returned ledger records a bound `xtack_id_precision` claim for numeric IDs. When precision is unverified, it omits the numeric `run_id` rather than presenting a rounded value. The claim separately records the numeric token observed in the current request or ledger when it is at most 4096 characters, or its length and SHA-256 when longer. That context does not establish original authorship or authenticate the source. A numeric ledger reevaluation records its latest observed token, so retain the original input or earlier ledger separately when needed. This token is not automatically used as an ID. A carried unverified claim cannot be bypassed by changing the ID to a string; explicitly supply the correct decimal ID in a fresh request without stale metadata. An older numeric ledger without a valid claim remains unverified, and a previously rounded input cannot be reconstructed from its parsed value. GitHub response numeric IDs are compared using their original positive decimal integer token, not a rounded JavaScript number. Claims are structural, not authenticated. Older schema validators may reject the extended claim; older executables ignore it and do not provide this protection.

For required CI, the core compares declared target files with their unfiltered Git index blob identities and executable modes, in addition to checking that the index is clean relative to HEAD. A mismatch or unavailable comparison is unverified; normal CRLF, LFS, encoding and other checkout transformations can cause this result. Empty directories and unsupported entries are unverified, as is executable-mode verification on Windows. This check does not prove the remote CI checkout used identical bytes or cover inputs outside the declared target. Older results did not perform this comparison; reassess affected CI evidence with the current core. Git commands, including status, can execute locally configured filters. The core snapshots the target again after the final Git checks to detect a lasting change there; earlier versions could miss a filter change made after the preceding snapshot. This does not detect all transient changes or prevent filter side effects. CI collection requires its initial target snapshot to match the target used for the gate assessment. Older core versions could combine gate evidence and CI results from different targets if the target changed before CI collection; reassess affected results with the current core. Declared target paths are passed literally when checking ignored files. Older core versions could interpret pathspec-like names as Git patterns and miss ignored inputs inside the target; reassess affected CI evidence with the current core.

`approval` is optional. If required, supply `delivery: {action, scope}` and an approval with matching `action`, `scope`, and `target_identity` from the observed target, plus `required`, `status`, and `reference`. For example, `delivery: {action: 'deploy', scope: 'staging'}` can be paired with `approval: {required: true, status: 'approved', action: 'deploy', scope: 'staging', target_identity: actualSnapshot, reference: 'host://actual-approval'}` where `actualSnapshot` is the actual snapshot result. Missing, different or stale target/action/scope is unverified; a denial matching the current action and target blocks delivery eligibility. This records a declared approval for conditional assessment, without conferring or authenticating authorization. The host's actual permissions remain authoritative.

Provide only explicitly requested limits, such as `"limits":{"tokens":{"max":10000,"usage":{"value":3000,"source":{"kind":"host","reference":"host://actual-usage"}}},"retries":{"max":5,"usage":{"value":2,"source":{"kind":"ledger","reference":"host://actual-attempts"}}}}`. Supported dimensions are `time_ms`, `tokens`, `cost`, and `retries`; cost additionally needs `currency`. With a supplied usage and source, the result is `within` or `exhausted` (`used >= max`); `exceeded` separately means `used > max`. Missing usage or source, including an exact unknown placeholder as its reference, is `unverified`. The aggregate `limits.status` still shows `exhausted` when any item is exhausted; the gate separately checks every item's status, so an unknown limit makes an otherwise eligible assessment unverified. These are calculations over caller-provided data, not authenticated host accounting, and no default limit is invented. At a cap, `next_actions` tells the coordinator to stop the relevant additional work or retries; an already satisfied evidence assessment does not become a failure merely because a cap was reached exactly. An exceeded declared limit blocks policy eligibility. The host remains responsible for enforcing its own limit and lifecycle.

For each requested limit the core checks whether the JSON number tokens for `max` and `usage.value` represent the same decimal values as the JavaScript Numbers it will compare. Equivalent spellings such as `0.30` and `3e-1` are accepted. If parsing lost a distinction or source collection fails, that limit is `unverified`; other valid limits are assessed independently. An exactly represented cap remains `exhausted` and does not by itself invalidate an otherwise eligible result.

Cost usage without `usage.currency` is assumed to use the declared currency. If provided, `usage.currency` must be a disclosed nonempty string exactly equal to the declared currency, including case and whitespace. An unknown placeholder for either currency, an invalid usage currency, or a mismatch makes cost `unverified`; a missing or blank declared currency remains an input error. The core does not convert, infer, or authenticate currencies. The check is repeated for direct inputs and ledgers independently of the numeric precision claim. It cannot preserve uncertainty if the caller removes or alters the explicit usage currency: the resulting input is assessed from its current contents. Older executables may ignore conflicting units.

For budget precision, the core scans only the selected limits to collect their numeric tokens. It follows the last occurrence of duplicate object members and skips unrelated nested values without recursion. If budget source collection cannot be completed, affected limits remain unverified. Inputs without requested limits, snapshots and command runs do not require budget source collection. Separately, route and gate validate numeric tokens throughout the effective intent, even when no limits are requested.

New full ledgers carry an optional `xtack_precision` claim on each limit, bound to its values, kind, declared currency and precision status. A missing, unverified or inconsistent claim on a versioned ledger remains unverified when re-evaluated, including after the rounded JSON has been saved and reloaded. Copying a limit with such a claim into a direct request does not erase its uncertainty. A genuinely new measurement can be supplied in a fresh direct request without the old claim; the coordinator must verify that measurement and its source. The claim detects inconsistent reuse, not tampering or inaccurate host accounting. It cannot recover digits already lost before the CLI received its JSON, including values rounded by an earlier executable or caller. Older executables may ignore the claim and produce an optimistic result after rollback; do not rely on them to enforce this precision check.

JSON schemas describe the portable structure. Runtime semantic validation also rejects duplicate criterion/unit IDs, all-optional criteria, dependency cycles or unknown dependencies, unknown criterion references, escaping paths, and invalid policy booleans; schema validation alone cannot establish those cross-field conditions, real command outcomes, provenance, or permissions. Some incomplete or malformed external evidence is deliberately handled as `unverified` instead of being accepted as passing or aborting the entire assessment.
