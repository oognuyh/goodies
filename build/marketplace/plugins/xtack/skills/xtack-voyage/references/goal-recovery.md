# Voyage goal recovery

When a recovered goal names evidence, inspect that exact permitted path directly before deciding it is absent or creating a replacement. General file listings and searches can omit ignored or hidden files; absence from those results is not evidence of absence. A relative reference does not by itself say whether it is relative to the goal directory, the original working directory, or another root. Use an observed anchor when available; otherwise inspect plausible permitted locations and report the location as unverified if it cannot be established. A candidate's existence alone does not authenticate it. Preserve existing receipts and earlier evidence, even when stale or insufficient. If a new check is needed, use a new permitted path without overwriting an existing artifact, link it separately, and retain the original observation and any provenance gap.

When recovering a host event or reviewer thread ID requires host-specific retrieval, consult the applicable [Codex](adapters/codex.md) or [Claude Code](adapters/claude-code.md) guide within the user's boundaries. Check the actual accessible host and store before concluding an original result is unavailable; an unattempted lookup is not evidence of absence. Do not start a service or write state when the request prohibits it, and report any unverified recovery gap.

When assessing a recovered independent review or its provenance, consult the review-provenance guidance in [Voyage delegation](voyage-delegation.md), including for a read-only goal review. Apply it within the permitted boundaries; consulting it does not authorize a new reviewer or evidence file.

The bundled store is `scripts/voyage-goal.mjs`; `show` reads a JSON object from stdin with `file` set to the goal directory and optional `goal_id` and `minimum_revision`. Do not invent a different command or bypass a reported identity conflict. If the guide or command is unavailable, use permitted file tools to inspect records only in the explicitly identified goal directory when possible. For current state, a complete listing whose numeric JSON filenames are all canonical positive safe integers from 1 without gaps can identify the highest visible record; check its version and embedded ID and revision against its filename and any independent anchor. Inspect earlier records or evidence within the permitted scope when the request needs them; report an incomplete listing, invalid name, conflict or other uncertain state. Direct file reads do not establish that the store validated the hash chain, that no later revision was deleted, or that records are authentic.

When individual goal revisions must be identified, read and associate one revision with its requested path before reading the next, unless a permitted tool explicitly labels each returned content with its target path. Check the embedded goal ID and revision against the selected file and any independent anchor; if the association cannot be established, report it unverified. This does not authenticate the records or verify their hash chain.

If an available persisted goal reclassifies a prerequisite as incomplete or unverified, assess its actual evidence, target, conditions, and required review provenance. If the evidence is stale, repair and verify that prerequisite within the authorized scope before editing its dependent unit. Otherwise reconnect still-valid evidence without rerunning an unchanged check solely to restore its status. Restore the justified prerequisite completion in the goal before editing the dependent unit; do not combine independent prerequisite and dependent edits merely to avoid this step. If a user requires a particular order, assess it against actual host observations and report any unverified gap; a final passing artifact or goal record alone does not prove the edit history. If the evidence or update is unavailable, leave that dependent work blocked, continue independent work, and report the gap. When a record is prohibited or unavailable, use the existing session-only fallback rather than creating one.

On a continuing turn or after interruption, recover the explicitly identified Voyage record when available, the original request and applicable later steering, xtack instructions, current artifacts, evidence, incomplete units, and next action before making changes. If no record is identified, check relevant permitted host session context and prior reports for a goal locator and compare any candidate with the actual request, target and available identity anchors. A unique search result or matching request alone does not establish continuity; do not select or modify an ambiguous candidate. If the record cannot be identified or read, use the actual host session and other permitted evidence without inventing missing state; report any recovery gap. A stored claim is not authenticated: inspect the current target and verify changed inputs, requirements and evidence again. When assessing a recovered completed goal or met criterion, compare its actual wording and linked evidence with the original request and applicable steering, even in a read-only session; report contradictions and unverified claims rather than relying on the stored status. Reconcile actual results with the original request before marking the Voyage goal complete. If the host did not reload this skill, recover its instructions from the installed skill file when available; report the limitation if they cannot be recovered.
