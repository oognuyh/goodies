# Claude Code host boundary and continuation

Selecting Voyage to coordinate the user's outcome starts its own goal. A separate reviewer consulting these instructions to assess an existing goal does not start or continue that goal; review the permitted record and evidence and return the result to its owner. When coordinating, use the bundled file-backed goal record in a permitted writable location when available; otherwise manage the goal in the current session and report that durable recovery is not assured. Claude Code owns the session, permissions, available tools, and any host task state. Honor applicable host instructions, constraints, and permissions; do not assume a background scheduler exists.

Claude Code can resume a prior conversation with `--resume` or `--continue`; this recovers a session, not a host-enforced completion condition or a promise of automatic continuation. On continuation, recover only the explicitly identified Voyage record and the user's original request, steering and constraints from available session context and permitted records. If the record cannot be read, report the gap and use available evidence without inventing state. Inspect the current target, prior results, and unfinished work; recheck evidence whose target or conditions changed. Record completion only after verifying the actual evidence and original outcome. Use an existing task list or project convention only when actually available and appropriate; it does not automatically synchronize with the Voyage record.

When recovering original session evidence matters and retention is permitted, Claude Code may provide the current session ID as `CLAUDE_CODE_SESSION_ID` in a Bash or PowerShell tool subprocess. Read only that variable if the tool is available. Associate a nonempty ID with the relevant observation in the existing goal evidence; do not treat the ID itself as proof, a transcript path, or a guarantee of persistence. A later host invocation can explicitly use `--resume <session-id>` when the session and its configuration are accessible. Stay within the permitted read scope and retain only what is needed; a transcript may contain unrelated sensitive material. Verify that the original observation can actually be reopened before relying on it; do not guess a transcript path or search outside permitted boundaries. The variable may be unavailable and session persistence may be disabled, including with `--no-session-persistence`; report any resulting recovery gap. Resumption does not start a new host invocation automatically or replace checking the current target.

Distinguish a host-observed tool-use or result identifier from the tool result's contents: do not label the contents as an identifier or invent an event identifier. Do not copy result contents into the goal when the user prohibits it. If an original result cannot be identified or reopened as required, keep that criterion unverified; recording a session ID alone does not satisfy it.

When required for an independent review or ADR stakeholder position, use a separate subagent context and supply the original outcome, requirements, scope, constraints, current target and relevant evidence explicitly. Do not treat a different model, an agent-authored claim, or a shared workspace alone as proof of independence. For a new ADR-worthy decision, two distinct subagents provide positions before the coordinator records the decision and starts dependent work. If the host cannot establish the required separation or supply the agents, leave the dependent decision unverified and continue other authorized work.

A separate review context does not necessarily require an isolated worktree. When permitted, select a read-only review of the actual shared workspace if that is how the reviewer can access uncommitted changes. If the host instead creates a worktree, its current directory may contain only the committed baseline: identify the user's allowed project root and actual target path explicitly, distinguish them from the reviewer's current directory, and ask it to verify the files and evidence it could read. Do not broaden the user's boundary or bypass a host denial. A new Agent call is a new context, not a continuation of another reviewer's access or conversation. If the actual target is unavailable, keep the affected review unverified rather than treating a baseline review as a review of the change.

For a background subagent, use the completion notification or an actually available host status mechanism for its task; an `Agent` call that asks for its status can instead start a new task. If a completed review needs additional work, Claude Code may provide `SendMessage` to resume the same agent by its ID; this starts another run and is not a status poll. Resuming may fail if the earlier agent transcript is unavailable; inspect the actual host result rather than assuming it resumed. When available and permitted, the host may also let you send changed scope to a running agent by ID; verify which target its returned review actually covers. If no suitable mechanism is available, do not invent one or duplicate the task solely to check progress; report any required review that cannot be established as unverified.

The official [environment variable reference](https://code.claude.com/docs/en/env-vars), [skills guide](https://code.claude.com/docs/en/skills), [subagent guide](https://code.claude.com/docs/en/sub-agents), and [session resumption guide](https://code.claude.com/docs/en/common-workflows#resume-previous-conversations) describe host capabilities; verify what is actually enabled and available in the current session. Local execution receipts and a gate assess supplied records but do not authenticate their origin, enforce host actions, or authorize delivery.
