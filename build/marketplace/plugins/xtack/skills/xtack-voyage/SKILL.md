# Xtack Voyage

Selecting Voyage to coordinate the requested outcome starts a Voyage goal; an independent reviewer consulting it does not start or continue the goal. Honor an explicitly requested start or resume. Own the user's actual outcome, scope, stopping point, exclusions, constraints, and later steering. Do not expand a plan, diagnosis, review, or verification into implementation. For unattended work, investigate and make delegated decisions without an interactive interview.

## Load the required guidance

Read the relevant guidance before relying on it; retrieve any truncated portions. If required instructions or tools cannot be accessed, honor the user's and host's boundaries, continue independent authorized work, and report the affected decision, check, persistence or recovery gap as unverified; do not claim completion of the dependent step without the required guidance.

If the requested work is limited to a read-only review of an explicitly identified saved goal and its evidence, read [goal recovery](references/goal-recovery.md) and inspect the original request, current record, relevant evidence and target within the permitted boundary. If reads are restricted to the repository, search inside it, not from its parent or through siblings; report an observed boundary violation. Use the store's `show` help when needed, retaining independently observed ID and revision anchors; report identity, authenticity, historical and evidence gaps. Assess tool and test side effects before running them: even `GIT_OPTIONAL_LOCKS=0 git diff` can refresh the index. When writes are forbidden, use only observations whose side effects are established to be permitted, or report the affected evidence as unverified; an independently owned copy is an option only if creating it is permitted. Do not create or update the goal, edit product files, or start another reviewer merely because you are reviewing it. Read other references only when their details are needed to answer the review. The following coordinator guidance applies when carrying out or updating a goal, including when a user authorizes record changes.

- Before deriving scope, choosing risk or editing, read [scope and risk](references/voyage-scope-risk.md) and [goal lifecycle](references/voyage-goal-lifecycle.md). These preserve the common requirements and the conditions under which a goal record may be used.
- Before carrying out any Voyage outcome, including planning, design, investigation, review or verification, read [execution and evidence](references/voyage-execution.md); reading it does not authorize implementation. Before delegating or relying on a recoverable review or other original observation that must be recoverable, also read [delegation](references/voyage-delegation.md).
- For continuation, interrupted work, unavailable store reads, multiple revisions, or an incomplete or unverified prerequisite, read [goal recovery](references/goal-recovery.md) before evaluating or acting on the recovered goal, including read-only review. Reassess identity, evidence and current state; report unestablished facts instead of inventing recovery.
- For an ADR-worthy decision, read [ADR decisions](references/adr.md) before the decision and dependent work. Consult the applicable [Codex](references/adapters/codex.md) or [Claude Code](references/adapters/claude-code.md) guide when host-specific discovery, delegation, continuation or session evidence matters.
- When coordinating a goal and permitted storage is available, create or explicitly resume its record using the [goal store guide](scripts/GOAL.md). A separate reviewer only inspects the existing goal, and a review-only request does not itself authorize a record; use session state when storage is prohibited or unavailable. When selecting the execution core, read its [quickstart](scripts/QUICKSTART.md). Read each guide separately. Consult the selected routing and playbook as described in execution and evidence.

## Coordinate the outcome

Apply the user's read and write boundaries to all work, including shell redirections, scratch files, records, tests, delegation and external calls. If writes are limited to a goal record, `git write-tree` is not a read-only check: it can update the index or create Git objects, even with `GIT_OPTIONAL_LOCKS=0`. Use a permitted observation or report the gap. Never overwrite or discard pre-existing user changes without authorization, bypass host denials, or silently narrow the request. Capture relevant pre-existing state before changes when preservation is required. Do not infer compliance with an explicit action prohibition throughout the work from final snapshots or incomplete logs alone; report the actual observations and material gaps.

When coordinating and storage and the bundled store are permitted and available, create a new goal or resume the explicitly identified one before the next product edit; if Voyage was selected after earlier edits, record their actual state without implying earlier planning. Inspect the returned identity and revision. If storage is unavailable or prohibited, continue in session state and report the persistence or recovery gap. A goal record is not authenticated and cannot enforce host actions or start a new turn.

Derive observable completion criteria and units from the original request and applicable steering. Identify each unit's result, scope, checks and dependencies; keep changes reviewable and preserve actual prerequisite or user-required ordering. Verify a unit before recording it complete, and link its actual permitted evidence to the criteria it supports. Keep criteria whose full scope is not established pending or unverified, including shared criteria; reassess evidence after relevant target or requirement changes. Independently owned units may proceed in parallel with separate checks. Keep inseparable changes together. Report actual ordering and any unverified requirement rather than presenting a planned sequence as an observation.

Classify effort from impact, reversibility, uncertainty and affected users. Light localized work needs relevant checks; Standard implementation requires independent requirements and standards review plus relevant execution checks; Critical work adds checks and review for actual risks such as data loss, recovery, concurrency or security. Do not downgrade risk merely because a change is small. For a non-implementation request, use checks appropriate to that deliverable and stop at the requested scope.

A decision is ADR-worthy when reversal has meaningful cost or impact, real alternatives have materially different consequences, and maintainers need the rationale. Reuse an applicable ADR. For a new ADR-worthy decision, before deciding and dependent work, obtain independent positions from at least two distinct native subagents, compare their actual responses, decide as coordinator and record the ADR. If required positions or the ADR cannot be obtained, leave that decision and dependent work blocked, continue independent work and report the gap.

Select only useful specialists. For required independent review use a fresh context separate from implementation; supply the actual original request or its accessible source, later steering, target, boundaries and relevant evidence. Do not rewrite a coordinator summary as a second original request. A self-review, file or digest alone does not establish independence or provenance. Address failed checks and blocking findings; recheck affected evidence after changes. A missing required assessment or check remains unverified. Retain and report accepted minor findings and their rationale.

Reconcile every required criterion against actual current evidence and the original request before completion. For new Standard/Critical core workflows, use `gate` with the actual reviewer disposition; do not infer it from passing review axes. For implementation using the core, inspect the current gate's overall `assessment` and required review results before updating the goal: an `unverified` or `blocked` assessment prevents completion until its reasons are resolved. If a selected core's required receipt or current gate is missing, do not complete the goal as if it ran; keep the affected criteria unverified, continue any independent work, and report the specific gap. Keep affected criteria unverified and the goal open; do not turn an independent review's unverified historical action into a pass solely from your own unauthenticated account or a final snapshot. A status, plan, green generic test or eligible gate alone does not prove every requirement, authentic review, preservation or historical ordering. Reuse evidence only while its target and conditions remain valid; report unmet or unverified criteria and gaps instead of claiming completion. The execution core evaluates supplied evidence but cannot authenticate claims or enforce host actions.

Follow project conventions for plans and documentation. Apart from a permitted Voyage goal record, create durable records only when they serve the work or are requested.
