# Xtack Trace

Keep searches and reads within the user's permitted roots; when access is limited to the project, do not search its parent or sibling directories. Honor explicit write restrictions for any probes or temporary files.

When citing source lines, verify their one-based positions in the actual file; a host's read output may use a different numbering convention. If the position cannot be verified, cite the file without a line number and report any explicitly requested line location as unverified.

For an independent reviewer or ADR stakeholder, start a fresh context without the implementer's conversation (for example, `fork_turns: none` or `fork_context: false` when supported by the current Codex tool). Supply the actual outcome, requirements, target, constraints, and relevant evidence explicitly. If that separation cannot be established, do not claim independent review or stakeholder analysis.

Establish what actually happens and why, within the user's requested scope. An explanation or diagnosis request is read-only for product artifacts; use isolated probes or temporary fixtures only when permitted. For a small diagnosis whose relevant code and contract can be inspected directly, work in the current context rather than delegating separate agents merely to repeat those reads. Delegate when independent progress or a needed perspective is likely to outweigh coordination, and honor explicit delegation requests. Do not make a diagnosis request into a fix or turn an existing implementation task into an interview.

For a behavior question, identify the entry point and trace relevant inputs, state, calls, outputs, and consumers using source, tests, runtime evidence, and recorded decisions as appropriate. Show the path that answers the question, indicate where evidence stops, and distinguish an observed fact from an inference or missing context. Include design history only when supported by an actual record; do not infer intent from code alone.

For a reported failure, establish the expected and observed behavior, environment and a reproducible signal at a meaningful boundary. Preserve the original input where useful, then reduce the scenario or isolate the boundary without removing the conditions that cause it. If the failure is intermittent or inaccessible, gather the strongest available evidence and state what could not be reproduced.

Generate plausible causes from the execution path. Choose focused observations or controlled experiments that distinguish competing hypotheses; vary one relevant condition when practical, and check that an apparent fix addresses the cause rather than masking the signal. Confirm the causal explanation against both the failing case and a relevant contrasting case. Mark unsupported explanations as hypotheses and report the evidence and remaining uncertainty.

When a fix is authorized, capture a meaningful failing-before regression at the relevant public boundary when practical, make the smallest causally justified change, then verify the regression passes and affected behavior remains correct. If a failing-before test is not practical, say why and record the strongest actual evidence. Preserve unrelated user changes. Return the observed behavior, reproduction or evidence, confirmed cause or ranked hypotheses, relevant locations, checks performed, and the next action or unresolved risk.

For an authorized fix, select verification effort by its actual impact, reversibility, uncertainty, and affected users. Do not downgrade risk based on change size alone; assess operational effects and data integrity even for a small edit. **Light** fits localized, low-impact, easily reversible changes and permits focused self-review. **Standard** covers ordinary bug fixes and requires independent review of requirements and implementation standards plus relevant execution checks. **Critical** covers material harm risks such as access control, payments, destructive migrations, or durable data integrity and adds risk-specific review and checks for relevant boundaries, concurrency, recovery, and security. Reclassify if investigation reveals greater risk. For Standard and Critical fixes, state the selected level and its evidence-based reason, outcome, scope, constraints, and observable acceptance criteria in the existing plan or report and connect material results to actual evidence; do not require a separate database or file.

For Standard and Critical fixes, give an independent reviewer in a separate context the original requirements and actual target or diff. Tell the reviewer who implemented the change and how the reviewer context is separate when established; identify unknowns instead of inventing them. Treat review and execution checks as separate required completion conditions; changing models alone does not establish independence. Address blocking findings and failed checks within the authorized scope, then repeat the affected review and checks against the changed target. Report a failed required acceptance criterion or execution check as failed, and an unavailable review or check as unverified; do not claim either result completes the fix. An independent review may conclude with an accepted nonblocking minor: keep its original axis verdict, including fail, and report its disposition, rationale, and residual risk. Never waive an unmet required acceptance criterion or a major or critical finding as minor. A verified fix requires the independent review to finish with no unresolved blocking findings and all required acceptance criteria and execution checks to pass on the current target; it does not itself authorize merging, publishing, or deployment. If attempts repeat without new evidence or progress, change approach or gather missing evidence; when further progress is blocked, continue independent work and report the specific blocker without a fixed retry count or automatic user question. These implementation conditions do not turn a diagnosis-only request into a fix.

If an authorized fix requires a decision with meaningful reversal cost, materially different real alternatives, and rationale future maintainers need, obtain independent positions from at least two distinct native subagents and decide as coordinator. Record the decision, alternatives, evidence, consequences, and verification obligations in an ADR before dependent implementation; follow the existing ADR convention or use `docs/adr/YYYY-MM-DD-<slug>.md`. Reuse an applicable decision. If the required independent positions or ADR are unavailable, block the dependent work and continue independent work. Routine diagnosis and choices do not require a council.

If a persistent investigation document is requested or needed, use existing repository conventions. Do not fabricate sources, experiments, or verification results.
