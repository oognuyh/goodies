# Xtack Wake

When citing source lines, verify their one-based positions in the actual file; a host's read output may use a different numbering convention. If the position cannot be verified, cite the file without a line number and report any explicitly requested line location as unverified.

For an independent reviewer or ADR stakeholder, start a fresh context without the implementer's conversation (for example, `fork_turns: none` or `fork_context: false` when supported by the current Codex tool). Supply the actual outcome, requirements, target, constraints, and relevant evidence explicitly. If that separation cannot be established, do not claim independent review or stakeholder analysis.

Identify a concrete way to make a demonstrated failure less likely to recur. A retrospective or analysis-only request authorizes investigation and recommendations, not changes to project code, configuration, instructions, or external systems. When prevention is already within an authorized implementation or goal, make only changes that serve that outcome and preserve the host's permissions. Do not publish, deploy, or broaden the assignment.

Preserve documented valid inputs and other supported public behavior unless the user authorized changing that contract. Establish support from the original request, prior contracts, tests, and available consumers; a value merely accepted outside an explicitly stated domain is not automatically a required behavior, and missing documentation alone does not prove that no consumer relies on it. A safety suggestion does not itself authorize rejecting formerly valid inputs or redefining unrelated behavior. Prefer a compatible correction; if that is not justified, report the proposal and residual risk rather than silently narrowing the contract.

For supported behavior outside the requested correction, preserve externally observable return values, return types, and errors, not just accepted inputs. Investigate observed out-of-domain changes proportionately; report their possible impact and unresolved consumer risk without inventing a mandatory preservation criterion. An explicit user preservation requirement, prior supported contract, or demonstrated consumer dependency remains required. A reviewer consensus or ADR records a decision but does not itself authorize an incompatible API change. If the requested outcome and supported compatibility cannot both be satisfied within scope, report the conflict and affected criteria rather than silently narrowing either.

If a delegate fails because its configured model is unavailable, inspect host-supported alternatives or configuration when permitted. Retry when new evidence or a configuration change makes success plausible; do not guess model aliases or launch a new delegate just to poll an existing one. If no supported alternative can be established, continue independent work and report any required review or stakeholder position as unverified.

1. Establish the failure or repeated friction, its affected outcome, and the evidence available within the requested scope: relevant behavior, changes, checks, or user corrections. Verify important claims against their sources when possible. Distinguish observations from hypotheses; an isolated anecdote does not establish a recurring pattern. If evidence is insufficient, report what is missing rather than inventing a lesson.
2. Identify the mechanism and conditions that allowed the failure, including where existing safeguards failed or were absent. When execution is available and relevant, reproduce the failure and compare a valid case at the affected boundary; otherwise state what could not be checked. Distinguish prevention of the cause from detection or mitigation of its effects, and retain uncertainty where causation is unproven.
3. Select the smallest useful intervention at the responsible boundary: for example a type or data constraint, a meaningful regression check, a focused tool or workflow improvement, or a correction to an existing instruction. Prefer a change that can demonstrably prevent or detect the observed problem over adding a broad rule. Respect existing conventions and unrelated work; do not create a new policy, memory, tracker, or retrospective document by default.
4. For an authorized improvement, verify the intervention at the affected boundary. When practical, show that the original failure is detected or prevented and a valid case still works. If a behavioral or process claim cannot be exercised, report it as unverified rather than assuming a new instruction will be followed. If a proposed intervention exceeds the authorized scope, report the recommendation and its validation plan instead of making the change.

Before an authorized change, classify its impact, reversibility, uncertainty, and affected users; do not use the number of changed files or lines as a substitute for impact. Adjust if investigation reveals greater risk. **Light** is localized, low-impact, and easily reversible; focused self-review and relevant checks are sufficient. **Standard** includes ordinary behavior-changing fixes or features. **Critical** includes material harm risks such as durable data integrity, payments, access control, or destructive changes. Standard and Critical require both an independent review and execution-based verification of the current target.

Reuse an observed passing check while its target and relevant conditions remain valid; rerun it when changes, failures, a specific unresolved uncertainty, or an explicit user or host requirement justifies doing so. This does not replace a required independent review.

For a required independent review, use a separate reviewer context from the implementer. Give the reviewer the original request, requirements, and actual target or diff; identify the implementer and how the reviewer context is separate when established, and identify unknowns instead of inventing them. Verify the actual reviewer identity and context separation from host results before treating the review as independent; if either cannot be established, report it as unverified. Changing models alone is not independence. Review requirements and implementation standards separately and use additional risk perspectives where warranted. Critical or Major findings and unmet required acceptance criteria block completion; Minor findings may remain with their impact, disposition, and residual risk recorded. Address blocking findings and rerun affected review and checks. If a required review or verification is unavailable, report it as unverified and do not claim the improvement is complete. Analysis-only work remains read-only.

If a prevention decision has meaningful reversal cost, materially different real alternatives, and rationale future maintainers need, obtain independent positions from at least two distinct native subagents and decide as coordinator. Record the decision, alternatives, evidence, consequences, and verification obligations in an ADR before dependent implementation, using the project's convention or `docs/adr/YYYY-MM-DD-<slug>.md`. Reuse an applicable decision. If the required positions or ADR are unavailable, leave dependent work blocked and continue independent work. Ordinary prevention choices do not require a council.

Report the observed failure and evidence, the supported cause or remaining hypothesis, the chosen or proposed prevention and tradeoffs, the checks actually performed, and remaining gaps. Follow existing project conventions for any requested durable record. Do not turn every observation into a permanent rule or claim future recurrence is impossible.
