# 문서 종류별 예시

## 이 예시를 쓰는 법

- 모든 예시는 가상의 상황이다. 문체의 기준이지 정답 틀이 아니다.
- 주제, 제목 구성, 문장, 부서명, 연락 방법, 업무 지시, 목록 항목을 가져오지 않는다. 구성은 입력에 있는 정보에 맞춰 정한다.
- 문장 구성, 연결 방식, 괄호와 목록을 쓰는 방식을 참고한다. 예시마다 종결형이 다르므로, 결과물에는 [공통 원칙](../SKILL.md#공통-원칙)에서 선택한 문체를 적용한다.
- 같은 내용도 여러 방식으로 잘 쓸 수 있다. 6절에 같은 내용을 두 방식으로 쓴 예가 있다.
- 각 예시 뒤의 "볼 점"은 그 예시가 지킨 규칙이다.

## 목차

1. 절차문: 웹 서버 TLS 인증서 교체
2. 설명문: API 요청 제한 방식
3. 공지문: 정보가 넉넉할 때와 적을 때
4. 보고서: 결제 승인 지연 장애 보고
5. 번역문: CDN 캐시 안내
6. 같은 내용을 두 방식으로: 백업 보관 기준
7. 고쳐 쓰기: 공공기관 자료의 원문 예

## 1. 절차문: 웹 서버 TLS 인증서 교체

<example>
### 웹 서버 TLS 인증서 교체

인증서가 만료되기 전에 새 인증서로 바꾸는 절차다. 작업은 20분 안팎 걸린다. 작업하는 동안 서비스는 멈추지 않는다.

**준비물**

- 새 인증서 파일과 개인 키 파일
- 웹 서버의 관리자 권한

**절차**

1. 새 인증서의 만료일을 확인한다.
   ```bash
   openssl x509 -in new.crt -noout -enddate
   ```
   만료일이 오늘보다 1년 이상 뒤인지 본다.
2. 기존 인증서와 개인 키를 백업 디렉터리에 복사한다. 백업 파일의 내용이 원본과 같은지 확인한다.
3. 새 인증서와 개인 키를 `/etc/nginx/tls/`에 복사한다. 대상 파일의 내용이 새 파일과 같은지 확인한다.
4. 설정 문법을 검사한다.
   ```bash
   nginx -t
   ```
   `syntax is ok`가 나오지 않으면 다음 단계로 넘어가지 않는다. 2단계에서 백업한 파일을 되돌린다.
5. 설정을 다시 읽는다.
   ```bash
   systemctl reload nginx
   ```
   명령의 종료 코드가 `0`인지 확인한다.
6. 브라우저로 사이트에 접속해 인증서 만료일이 바뀌었는지 본다.

> 개인 키 파일을 메일이나 메신저로 보내지 않는다. 키가 유출되면 인증서를 폐기하고 다시 발급해야 한다.
</example>

볼 점
- 첫 문단에 작업 내용, 걸리는 시간, 서비스에 미치는 영향을 썼다.
- 한 단계에 동작 하나를 썼다. 동작 뒤에 확인할 결과를 썼다.
- 실패 조건을 먼저 쓰고 할 일을 나중에 썼다.
- 위험 안내는 표지어 없이 인용 블록에 썼다. 지시를 먼저 쓰고 결과를 다음 문장에 썼다.

## 2. 설명문: API 요청 제한 방식

<example>
### API 요청 제한 방식

API 게이트웨이는 클라이언트마다 1분에 받는 요청 수를 제한한다. 한 클라이언트가 요청을 몰아 보내도 다른 클라이언트의 응답이 느려지지 않게 하려는 장치다.

제한은 토큰 버킷 방식으로 동작한다. 클라이언트마다 토큰을 담는 버킷이 하나씩 있다. 게이트웨이는 요청 하나를 처리할 때마다 버킷에서 토큰 하나를 꺼낸다. 버킷은 1초마다 토큰 10개씩 다시 찬다. 버킷에는 토큰을 600개까지 담는다.

버킷이 비면 게이트웨이는 요청을 처리하지 않고 HTTP 429를 돌려준다. 응답 헤더 `Retry-After`에는 다시 요청해도 되는 때까지 남은 초가 들어 있다. 클라이언트는 이 시간이 지난 뒤에 요청을 다시 보낸다.

제한값은 클라이언트 등급마다 다르다. 등급별 값은 운영 설정 파일의 `rate_limit` 항목에 있다.
</example>

볼 점
- 첫 문장에 요지를 썼다. 둘째 문장에 목적을 썼다.
- 문단마다 주제가 하나다. 개념, 동작, 실패할 때, 설정 순서로 나눴다.
- 행위자(게이트웨이, 클라이언트)를 주어로 세웠다.
- "토큰 버킷"을 처음 쓴 뒤 같은 말로만 불렀다.

## 3. 공지문: 정보가 넉넉할 때와 적을 때

### 3-1. 정보가 넉넉할 때

가상의 상황: 10월 20일(화) 18:00부터 18:30까지 사내 메신저 PC 버전을 업데이트한다. 그동안 메신저에 접속할 수 없다. 업데이트가 끝나면 메신저를 다시 시작해야 한다. 문의처는 IT지원팀이다.

<example>
### 사내 메신저 업데이트 안내

10월 20일(화) 18:00부터 18:30까지 사내 메신저 PC 버전을 업데이트합니다. 이 시간에는 메신저에 접속할 수 없습니다.

- 일시: 10월 20일(화) 18:00~18:30
- 대상: 사내 메신저 PC 버전

업데이트가 끝나면 메신저를 다시 시작해야 합니다. 문의는 IT지원팀(내선 ○○○○)으로 합니다.
</example>

볼 점
- 독자에게 영향을 주는 내용과 날짜를 첫 문단에 썼다.
- 상황에 있는 사실만 썼다. 일시와 대상처럼 나열할 정보는 목록으로, 할 일은 문장으로 썼다.
- 괄호에는 요일과 내선 번호만 넣었다. ○○○○는 실제 번호가 들어갈 빈자리다.

### 3-2. 정보가 적을 때

가상의 상황: 11월 7일(토)에 사내 위키 서버를 정기 점검한다. 점검 시간과 영향은 아직 정해지지 않았다.

<example>
### 사내 위키 정기 점검 안내

11월 7일(토)에 사내 위키 서버를 정기 점검합니다.

- 점검일: 11월 7일(토)
- 점검 시간: [점검 시간]
</example>

볼 점
- 주어진 사실은 날짜와 대상뿐이다. 제목과 목록으로 구성했지만 영향이나 할 일을 지어내지 않았다.
- 독자가 꼭 알아야 하는데 아직 없는 값만 빈자리로 두었다.

## 4. 보고서: 결제 승인 지연 장애 보고

<example>
### 결제 승인 지연 장애 보고

**요약**

10월 14일 14:05부터 14:47까지 42분 동안 결제 승인이 평소보다 20초 넘게 늦어졌다. 결제 DB의 연결 수가 상한에 닿아 생긴 장애다. 연결 수 상한을 올려 복구했다. 실패한 결제는 없다.

**경위**

- 14:05 결제 승인 응답 시간 경보가 울렸다.
- 14:12 당직자가 결제 DB의 연결 수가 상한(500)에 닿은 것을 확인했다.
- 14:30 연결 수 상한을 800으로 올렸다.
- 14:47 응답 시간이 평소 수준(0.8초)으로 돌아왔다.

**원인**

14:00에 정산 배치가 시작되면서 DB 연결을 300개 더 열었다. 배치는 일을 마친 연결을 닫지 않고 남겨 두었다. 그래서 결제 서비스가 새 연결을 얻지 못하고 기다렸다.

**재발 방지**

- 정산 배치의 연결 수 상한을 50으로 줄인다. 담당은 정산팀, 기한은 10월 21일(수)이다.
- DB 연결 수가 상한의 80%를 넘으면 경보를 보낸다. 담당은 운영팀, 기한은 10월 23일(금)이다.
</example>

볼 점
- 요약 문단 하나만 읽어도 무슨 일이 언제, 왜 일어났고 어떻게 끝났는지 안다.
- 수치는 기록에 있는 값만 썼다. 효과를 부풀리거나 예상치를 지어내지 않았다.
- 원인을 시간 순서대로 짧은 문장으로 이었다.

## 5. 번역문: CDN 캐시 안내

원문:

> Responses are cached by the CDN for up to five minutes. If you need users to see changes immediately, you can purge the cache from the dashboard. Note that purging the cache will increase the load on your origin server, as all requests will be forwarded to it until the cache is repopulated.

직역한 글 (나쁜 예):

> 응답은 CDN에 의해 최대 5분 동안 캐시됩니다. 사용자가 변경 사항을 즉시 보는 것이 필요한 경우, 대시보드로부터 캐시를 퍼지할 수 있습니다. 캐시를 퍼지하는 것은 원본 서버에 대한 부하를 증가시킬 것이라는 점에 유의하십시오. 이는 캐시가 다시 채워질 때까지 모든 요청이 원본 서버로 전달되어지기 때문입니다.

<example>
CDN은 응답을 최대 5분 동안 캐시에 저장합니다. 변경 사항을 사용자에게 바로 보여 주려면 대시보드에서 캐시를 비울 수 있습니다. 캐시를 비우면 원본 서버의 부하가 늘어납니다. 캐시가 다시 찰 때까지 CDN이 모든 요청을 원본 서버로 보내기 때문입니다.
</example>

볼 점
- "CDN에 의해 캐시됩니다"를 "CDN은 ~ 저장합니다"로 바꿔 행위자를 주어로 세웠다.
- "퍼지하다"를 "비우다"로 옮겼다.
- "you can purge"는 허용이라 "비울 수 있습니다"로 옮겼다. 지시로 바꾸지 않았다.
- "Note that"을 옮기지 않았다. 주의할 내용을 그대로 문장으로 썼다.
- 원문 셋째 문장을 두 문장으로 나눴다.

## 6. 같은 내용을 두 방식으로: 백업 보관 기준

내용이 같아도 독자와 쓰임에 따라 줄글과 목록 가운데 고른다. 둘 다 이 스킬의 규칙을 지킨다.

줄글로 쓴 예

<example>
운영 DB는 매일 03:00에 전체 백업한다. 백업 파일은 30일 동안 보관하고, 매월 1일 백업만 1년 동안 따로 보관한다. 보관 기간이 지난 파일은 백업 서버가 자동으로 지운다.
</example>

목록으로 쓴 예

<example>
운영 DB 백업 기준은 다음과 같다.

- 매일 03:00에 전체 백업한다.
- 백업 파일은 30일 동안 보관하고, 매월 1일 백업은 1년 동안 보관한다.
- 보관 기간이 지난 파일은 백업 서버가 자동으로 지운다.
</example>

볼 점
- 줄글은 설명 문서에, 목록은 운영 기준표처럼 빨리 찾아봐야 하는 문서에 맞다.
- 두 예 모두 수치와 용어가 같다.

## 7. 고쳐 쓰기: 공공기관 자료의 원문 예

국립국어원과 법제처 자료에 실린 고쳐 쓰기 예다. 행정 문장이지만 기술 문서에도 같은 원리가 적용된다.

| 고칠 표현 | 고친 표현 | 출처 |
|---|---|---|
| 확인서 발급에 따른 편의성을 제고함 | 확인서 발급에 따른 편의성을 높임 | 국어원 지침 p.7 |
| 허가를 득하여 | 허가를 받아 | 국어원 지침 p.7 |
| 필요한 제반 사항을 지원 | 필요한 모든 사항을 지원 | 국어원 지침 p.7 |
| 가능성은 상존하고 있다 | 가능성은 늘 있다 | 국어원 지침 p.7 |
| 일부가 도로로 사용 중에 있으나 | 일부가 도로로 사용되고 있으나 | 국어원 지침 p.7 |
| 민원 안내 자료 부족 등 문제점 도출 | 민원 안내 자료 부족 등 문제점이 발견됨 | 국어원 지침 p.24 |
| 당해상품이 일반소비자에 의하여 일상 사용되는 것일 것 | 해당 상품이 일반 소비자가 일상적으로 사용하는 것일 것 | 법제처 문장편 p.193 |
| 납세자는 그 의무를 이행함에 있어서는 신의에 좇아 성실히 하여야 한다 | 납세자가 그 의무를 이행할 때에는 신의에 따라 성실하게 하여야 한다 | 법제처 문장편 p.173 |

긴 문장을 나눈 예 (국어원 지침 p.12의 예시를 바탕으로, 원문의 조건을 보존해 이 스킬이 다시 쓴 예):

> 고치기 전: 위 대상자는 공고 기간 내 의견 제출(서면 또는 구술)을 할 수 있으며, 만일 정당한 이유 없이 의견을 제출하지 않을 경우, … 간주함을 알려 드립니다.
>
> 고친 뒤: 위 대상자는 공고 기간 내에 서면이나 구술로 의견을 제출할 수 있습니다. 정당한 이유 없이 의견을 제출하지 않으면 … 간주함을 알려 드립니다.

국어원 지침의 원래 고친 예는 "정당한 이유 없이"를 빼고 제출처를 더했다. 이 스킬은 고쳐 쓸 때 조건과 정보 범위를 바꾸지 않으므로 그 예를 그대로 싣지 않았다.

기술 문서를 고친 예 (이 스킬이 만든 예):

> 고치기 전: 본 문서는 로그 보관 정책의 변경에 대한 내용을 다룹니다. 보관 기간은 90일에서 30일로 단축되며, 이를 통해 스토리지 비용의 절감이 가능할 것으로 판단됩니다(단, 감사 로그의 경우 관련 규정에 따라 1년간 보관되어집니다).
>
> 고친 뒤: 로그 보관 기간을 90일에서 30일로 줄입니다. 그러면 저장 공간 비용을 줄일 수 있을 것으로 봅니다. 감사 로그는 관련 규정에 따라 1년 동안 보관합니다.

줄표 부연을 고친 예 (이 스킬이 만든 예):

> 고치기 전: 캐시는 강력한 도구다 — 하지만 만능은 아니다. 캐시를 쓰면 응답이 빨라지고 — 특히 읽기가 많은 서비스에서 — 원본 서버의 부하도 줄어든다. 결론: 캐시는 읽기 위주 서비스에 맞다.
>
> 고친 뒤: 캐시는 강력하지만 만능은 아니다. 캐시를 쓰면 응답이 빨라지고 원본 서버의 부하도 줄어든다. 이 효과는 읽기가 많은 서비스에서 특히 크다. 그래서 캐시는 읽기 위주 서비스에 맞다.
